## 序言｜你的大腦是怎麼看待「Claude 技能」的？

### 🧠 大腦小劇場

```
你的大腦：「欸，又一本技術手冊？直接丟到長期記憶垃圾桶吧。」
你：「等等，這本不一樣，這跟我工作會用到。」
你的大腦：「隨便，反正我只記得你昨天吃什麼。」
```

**這就是為什麼這本指南要用 Head First 風格寫。**

你的大腦天生會過濾掉「看起來很無聊的東西」。它演化的目的不是為了讓你記住 YAML 前言的 1024 字元限制，而是讓你記住「哪裡有劍齒虎、哪裡有食物、哪個部落的人會揍你」。

所以，我們要用你大腦**無法忽視**的方式來介紹 Claude 技能：故事、對話、比喻、視覺、驚訝、還有一點點「這跟我有關」的焦慮感。

## 第 1 章｜技能基本功：從資料夾開始的魔法

### 🔥 痛點場景

**場景：週五下午 4:45**

```
你：「Claude，幫我把這份客戶報告照我們公司的格式整理一下。
      記得要有封面、目錄、三級標題、頁碼，還要加上我們的
      Logo 浮水印，最後生成 PDF。對了，要繁體中文、
      報告風格要正式、段落要短、標題要用思源宋體……」

[15 分鐘後]

你：「不對不對，你忘了加目錄。」
Claude：「抱歉，讓我重新做。」
你：「還有浮水印的透明度要 30%。」
Claude：「好的。」
你：「你怎麼又用簡體字了？！」
```

**這是 2024 年的你。**

**2026 年的你，會這樣做：**

```
你：「Claude，幫我把這份報告整理成公司格式。」
Claude：[自動載入 company-report-generator 技能]
        [按照規範產出完美的 PDF]
你：「謝謝。」
[下班]
```

**差別在哪裡？差別就是——你教了 Claude 一次，而不是每次都教。**

### 🎓 技能到底是什麼？

> **定義（官方）**：
> 技能（Skill）是一套指令集，打包成一個簡單的資料夾，
> 用來教導 Claude 如何處理特定的任務或工作流。

**翻譯成人話：**

> 技能 = 一個資料夾 + 一個 SKILL.md 檔案 + 一些選配的腳本/文件/範本

就這樣。真的就這樣。

---

### 📂 技能資料夾的解剖圖

```
your-skill-name/              ← 資料夾，用 kebab-case 命名
│
├── SKILL.md                  ← ⭐ 必要！大小寫必須完全一致
│                                 （這是技能的「大腦」）
│
├── scripts/                  ← 選配：可執行的程式碼
│   ├── process_data.py       ← Python 腳本
│   └── validate.sh           ← Bash 腳本
│
├── references/               ← 選配：需要時才載入的文件
│   ├── api-guide.md          ← API 參考手冊
│   └── examples/             ← 範例集
│
└── assets/                   ← 選配：輸出用的資源
    └── report-template.md    ← 模板、字體、圖標等
```

### 🧪 **沒有蠢問題**

**Q：為什麼 SKILL.md 要這麼嚴格？**

A：因為 Claude 的系統是靠精確檔名來載入技能的。這不是人類在翻資料夾找「大概叫這個名字的檔案」，而是程式在做字串比對。`SKILL.md != skill.md`。

**Q：我可以只有 SKILL.md 嗎？不要 scripts/ 跟 references/？**

A：完全可以。最簡單的技能就是**一個資料夾 + 一個 SKILL.md**。其他都是選配。

**Q：資料夾名稱和 YAML 裡的 `name` 欄位需要一樣嗎？**

A：**強烈建議一樣**。雖然技術上可以不同，但這會讓維護變成惡夢。請取相同名字。

**Q：技能可以大到什麼程度？**

A：SKILL.md 主體建議控制在 **5,000 字以內**。更多的內容請放到 `references/`，讓 Claude 按需載入（這就是我們接下來要講的「漸進式揭露」）。

### 🎨 核心設計原則（三大支柱）

Claude 技能架構建立在三個核心原則上。不理解這三個，你寫出來的技能會又肥又慢又難維護。

#### 支柱 1：漸進式揭露（Progressive Disclosure）

**這是技能架構最重要的概念，請畫線、打星號、貼便利貼。**

想像你走進一間圖書館：

```
                       📚 圖書館（= Claude 的上下文）
                              │
           ┌──────────────────┼──────────────────┐
           │                   │                   │
    🪧 書目索引         📖 翻開的書           📦 書庫深處
   （總是看得到）    （當你有興趣才拿）      （要時才取）
           │                   │                   │
           ▼                   ▼                   ▼
    ═══════════════════════════════════════════════════
    第一層              第二層              第三層
    YAML 前言          SKILL.md 主體       references/
    ─────────          ──────────────      ─────────────
    永遠載入           相關時才載入         按需載入
    ~50-100 tokens    ~500-2000 tokens    視情況而定
    ═══════════════════════════════════════════════════
```

**這樣做的威力在哪？**

> 假設你有 50 個技能。如果全部都整包載入，你的上下文早就爆了。
> 但用漸進式揭露，初始成本只有「50 個名字 + 描述」≈ 5,000 tokens。
> 只有當 Claude 判斷某個技能真的相關，才會載入那個技能的完整內容。

**節省了多少？**
> 根據 Anthropic 官方數據：**初始上下文節省可達 98%**。

---

#### 支柱 2：可組合性（Composability）

**Claude 可以同時載入多個技能。**

你寫的技能不應該假設自己是唯一存在的。要像一個禮貌的鄰居：

```
❌ 差的技能：
「我是唯一存在的 AI 能力，一切都要聽我的！」
（會跟其他技能打架）

✅ 好的技能：
「我負責處理 Hugo 前端部分。如果碰到資料庫的事，
  那是另一個技能的專長，我不插手。」
```

---

#### 支柱 3：可移植性（Portability）

**同一個技能，在 Claude.ai、Claude Code、API 上都能跑。**

```
        ┌─────────────────┐
        │   你的技能資料夾  │
        └─────────┬───────┘
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   Claude.ai  Claude Code    API
        │          │          │
        ▼          ▼          ▼
     相同行為    相同行為    相同行為
```

前提是：環境要支援技能需要的依賴（例如 Python 套件、MCP 伺服器等）。

### 💡 **深度對話**：技能 vs. MCP

*訪談嘉賓：技能本尊 & MCP 本尊*

```
🎤 主持人：「兩位可以先自我介紹嗎？」

🔧 MCP：「我是 Model Context Protocol。我是連接器。
         我把 Claude 接到你的 Notion、Linear、GitHub、
         資料庫、API……只要是工具，我都能接。」

📜 技能：「我是 Skill。我不接任何工具，但我教 Claude
         『怎麼用』這些工具。我是食譜，MCP 是廚房。」

🎤 主持人：「所以你們是競爭關係嗎？」

🔧 MCP：「不，完全相反。沒有我，技能只是一張紙；
         沒有技能，我只是一堆工具躺在那裡，
         使用者要自己想辦法組合使用。」

📜 技能：「對，我們是最佳拍檔。」
```

**用表格看得更清楚：**

| 屬性         | MCP（連線層）                  | 技能（知識層）                    |
|--------------|-------------------------------|----------------------------------|
| **角色**     | 把 Claude 接到你的服務          | 教 Claude 怎麼有效使用服務        |
| **提供內容** | 即時資料、工具呼叫              | 工作流程、最佳實踐                 |
| **性質**     | Claude **能做什麼**            | Claude **應該怎麼做**             |
| **類比**     | 廚房、廚具、食材                | 食譜、烹飪技巧                     |

### ⚠️ 沒有技能的 MCP：常見慘案

你花了兩週做了一個很炫的 MCP 伺服器，上線後發現：

```
使用者 A：「我連上你的 MCP 了……然後呢？」
使用者 B：「我問 Claude 做 X，結果它呼叫錯 API 了！」
使用者 C：「每次對話我都要重新解釋怎麼用你的服務。」
使用者 D：「我覺得你的 MCP 爛透了！」（其實是他自己不會用）
```

**配上技能後：**

```
使用者 A：（輸入想做的事）
Claude：  [自動載入技能，按照最佳實踐執行]
使用者 A：「哇！這就是我要的！」
```

**練習 1：診斷命名**

以下資料夾名稱，哪些是合法的技能名稱？

```
☐ hugo-blog-builder
☐ Hugo Blog Builder
☐ hugo_blog_builder
☐ hugoBlogBuilder
☐ hugo-blog-builder-v2
☐ anthropic-hugo-builder
☐ hugo-blog-builder-2026
```

<details>
<summary>答案</summary>

✅ 合法：
- `hugo-blog-builder`
- `hugo-blog-builder-v2`
- `hugo-blog-builder-2026`

❌ 不合法：
- `Hugo Blog Builder`（有空白、有大寫）
- `hugo_blog_builder`（底線不允許）
- `hugoBlogBuilder`（駝峰式不允許）
- `anthropic-hugo-builder`（anthropic 是保留字）

</details>

**練習 2：檔案結構偵錯**

下面這個技能資料夾結構有什麼問題？（至少找出 3 個）

```
Smart Farming Podcast Generator/
├── README.md
├── skill.md
├── scripts/
│   └── generate.py
├── config.yaml
└── smart-farming-podcast-generator/
    └── SKILL.md
```

<details>
<summary>答案</summary>

問題一大堆：

1. ❌ 資料夾名稱 `Smart Farming Podcast Generator` 有空白
2. ❌ 主要檔案應該是 `SKILL.md` 不是 `skill.md`（大小寫錯誤）
3. ❌ 不該有 `README.md` 在技能資料夾內
4. ❌ 多餘的巢狀資料夾 `smart-farming-podcast-generator/`
5. ⚠️ `config.yaml` 這個位置不對，應該視用途放在 `scripts/` 或 `references/`

正確結構：

```
smart-farming-podcast-generator/
├── SKILL.md
├── scripts/
│   └── generate.py
└── references/
    └── config.yaml
```

</details>
