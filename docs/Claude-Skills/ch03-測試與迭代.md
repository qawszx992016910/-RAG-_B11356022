```
┌─────────────────────────────────────────────────────┐
│                                                      │
│  週一早上的開發會議                                   │

└─────────────────────────────────────────────────────┘
```

**這一章，就是在救小王。**

你的技能會遇到的不是「能不能跑起來」的問題——那是最基本的。真正的問題是：

- 🔥 使用者換一種說法，技能會觸發嗎？
- 🔥 使用者說一個完全無關的事，技能會不會錯誤觸發？
- 🔥 技能載入後，Claude 真的有照著你的指令做嗎？
- 🔥 有技能 vs. 沒技能，「真的」有比較好嗎？

這些問題，都不能靠「感覺」，要靠**測試**。

### 🎯 本章你會學到

- 三種測試層級（選對你需要的嚴格度）
- Anthropic 工程師的私房心法：「先單點磨，再擴展」

- 用 `skill-creator` 技能來建立/審查技能

**為什麼不要先寫技能？**

因為你還不知道「什麼是對的流程」。你花三天寫一個根本方向錯誤的技能，不如花半天先跟 Claude 對話、找出對的做法，再把它封裝起來。

### 🧪 推薦的測試三部曲

基於早期採用者的經驗，有效的技能測試通常涵蓋**三個面向**：

```
   1️⃣ 觸發測試       2️⃣ 功能測試        3️⃣ 效能比對
   ───────────      ─────────────      ─────────────
   技能有在           技能跑出來的         有技能 vs. 沒技能
   對的時機           結果對嗎？          是真的變好嗎？
   載入嗎？
```

接下來逐一拆解。

---

### 1️⃣ 觸發測試（Triggering Tests）

**目標**：確保你的技能在「對的時機」載入。

這是**最容易被忽略**但**最重要**的測試。

---

#### ✅❌ 兩種必測的案例

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 應該觸發的案例（Positive Cases）               ║
║     ▸ 明顯的任務                                   ║
║     ▸ 換句話說的請求（paraphrased）                ║
║                                                   ║
║  ❌ 不應該觸發的案例（Negative Cases）             ║
║     ▸ 無關的話題                                   ║
║     ▸ 看起來相關但其實不是的話題                   ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 📋 測試套件範例：ProjectHub 技能

假設你做了一個 `projecthub-setup` 技能。

**應該觸發：**
```
✅ "幫我設定新的 ProjectHub 工作區"
✅ "我需要在 ProjectHub 建立一個專案"
✅ "幫 Q4 planning 初始化一個 ProjectHub 專案"
```

**不應該觸發：**
```
❌ "舊金山今天天氣怎樣？"
❌ "幫我寫一段 Python 程式碼"
❌ "建立一個試算表" （除非你的技能有處理試算表）
```

### 2️⃣ 功能測試（Functional Tests）

**目標**：驗證技能產生「正確的輸出」。

觸發成功只是起點。技能載入後，真的做對事情了嗎？

---

#### 📋 必測的四個面向

```
┌─────────────────────────────────────────┐
│                                          │
│  ✅ 有產出有效的輸出嗎？                  │
│  ✅ API 呼叫成功嗎？                      │
│  ✅ 錯誤處理有在運作嗎？                  │
│  ✅ 邊界情況（edge cases）有處理嗎？      │
│                                          │
└─────────────────────────────────────────┘
```

---

#### 🧪 測試範例：建立專案 + 5 個任務

```
測試目標：建立一個含 5 個任務的專案

給定（Given）：
  ▸ 專案名稱 "Q4 Planning"
  ▸ 5 個任務描述

當（When）：
  ▸ 技能執行工作流

則（Then）：
  ▸ ProjectHub 中建立了專案
  ▸ 建立了 5 個任務，屬性正確
  ▸ 所有任務連結到正確的專案
  ▸ 0 個 API 錯誤
```

---

#### 🎯 **邊界情況檢核**

功能正常只是「及格」，真正見真章的是邊界情況。

```
常見邊界情況清單：

☐ 空輸入（使用者傳入空字串、空檔案、0 個項目）
☐ 超大輸入（1000 個任務、10GB 檔案）
☐ 特殊字元（中文、emoji、引號、換行符）
☐ 網路斷線（MCP 連線中斷）
☐ 重複執行（第二次執行同一個操作）
☐ 權限不足（API token 過期、沒有存取權）
☐ 檔案不存在（指定的檔案路徑是錯的）
☐ 格式錯誤（CSV 少欄位、JSON 語法錯）
```

**不是每個技能都要測這麼全，但以下是**最不能跳過的**：

- 🚨 如果你的技能會「寫入/修改外部系統」→ 必須測「重複執行」與「失敗回復」
- 🚨 如果你的技能會「處理使用者上傳的檔案」→ 必須測「格式錯誤」
- 🚨 如果你的技能會「呼叫 MCP」→ 必須測「網路斷線 + API token 過期」

### 3️⃣ 效能比對（Performance Comparison）

**目標**：證明技能真的**比原生對話好**。

這是最容易被忽略、但最能展現價值的測試。

---

#### ⚔️ 經典對決範例

```
┌─────────────────────────────────────────────────┐
│                                                  │
│  🥊 任務：建立一個包含 5 個任務的專案            │
│                                                  │
│  ═══════════════════════════════════════════    │
│  🔴 無技能（Baseline）                           │
│  ═══════════════════════════════════════════    │
│    ▸ 使用者要每次解釋流程                        │
│    ▸ 15 輪來回對話                               │
│    ▸ 3 次 API 呼叫失敗要重試                     │
│    ▸ 消耗 12,000 tokens                          │
│                                                  │
│  ═══════════════════════════════════════════    │
│  🟢 有技能                                       │
│  ═══════════════════════════════════════════    │
│    ▸ 自動執行工作流                              │
│    ▸ 只問 2 個澄清問題                           │
│    ▸ 0 次 API 失敗                               │
│    ▸ 消耗 6,000 tokens                           │
│                                                  │
│  ═══════════════════════════════════════════    │
│  📊 結果：節省 50% tokens、減少 87% 對話輪次     │
│                                                  │
└─────────────────────────────────────────────────┘
```

---

#### 📊 比對要看的三個數字

```
┌───────────────────────────────────────────────┐
│                                                │
│  1. 對話輪次（Conversation turns）             │
│     ──────────────────────────────            │
│     完成任務要幾輪來回？                        │
│                                                │
│  2. 工具呼叫次數（Tool calls）                 │
│     ────────────────────────                  │
│     成功的 + 失敗重試的                         │
│                                                │
│  3. Token 消耗量                               │
│     ─────────────                             │
│     輸入 + 輸出的總 token 數                    │
│                                                │
└───────────────────────────────────────────────┘
```

**提醒**：如果三個數字**都沒有顯著改善**，那你的技能可能設計得不夠好——或是這個情境根本不需要技能。

### 🔄 根據回饋迭代

技能不是「上線就結案」。它是**活的文件**。

你會持續收到三類訊號，每一類都有對應的解法。

---

#### 🚨 訊號 1：觸發不足（Undertriggering）

**症狀：**
```
▸ 該觸發的時候沒載入
▸ 使用者得「手動啟用」技能
▸ 客服收到「什麼時候該用這個技能？」的問題
```

**解法：**
```
在 description 加更多細節與變化

特別是要加入：
✅ 技術術語（使用者真的會說的）
✅ 同義詞 / 換句話說
✅ 具體的動詞（"建立"、"遷移"、"產出"、"審查"）
✅ 檔案類型（.pdf、.xlsx、.fig）
```

**實例**：

```yaml
# 🔴 改前（觸發不足）
description: 協助 Hugo 網站工作。

# 🟢 改後
description: Hugo 靜態網站的建置、遷移、與主題客製。
  當使用者提到「Hugo」、「靜態網站」、「SSG」、
  「MIDA Theme」、「WordPress 搬家」、「Ghost 搬家」、
  或上傳 .toml、.yaml、hugo.config 檔案時使用。
```

---

#### 🚨 訊號 2：過度觸發（Overtriggering）

**症狀：**
```
▸ 無關的查詢也載入了技能
▸ 使用者把技能關掉
▸ 對技能目的感到困惑
```

**解法：**
```
1. 加「負向觸發」（Negative triggers）
2. 描述更具體
3. 明確限定範圍
```

**實例**：

```yaml
# 🔴 改前（過度觸發）
description: 處理文件。

# 🟢 改後 - 加負向觸發
description: CSV 檔案的進階資料分析。
  用於統計建模、迴歸分析、分群演算法。
  【不要】用於簡單的資料探索（那是 data-viz 技能的工作）。

# 🟢 改後 - 具體化
description: 處理 PDF 法律文件的合約審查。

# 🟢 改後 - 明確限定
description: PayFlow 電商付款處理。
  專門用於線上支付工作流，不處理一般的財務查詢。
```

---

#### 🚨 訊號 3：執行問題（Execution Issues）

**症狀：**
```
▸ 結果不一致
▸ API 呼叫失敗
▸ 需要使用者糾正
```

**解法：**
```
改善指令 + 增加錯誤處理
```

**一些具體技巧（第 5 章會更深入）**：
- 把關鍵指令放到 SKILL.md 最頂端
- 用 `## 重要` 或 `## Critical` 標題強調
- 關鍵重點重複提醒
- 關鍵驗證用腳本（不要只依賴語言指令）

---

### 🎯 三個迭代訊號的決策流程圖

```
              觀察到技能有問題
```

### 🧯 **沒有蠢問題**

**Q：我已經跑過測試，技能動得很好。為什麼還要迭代？**

A：因為使用者的說話方式會變、MCP 會升級、需求會改變。「技能是活的文件」這句話的意思是：你的維護從上線那天才真正開始。

---

**Q：迭代要迭多久才算完？**

A：以你的成功標準（第 2 章定義的）為準。觸發率 90%、0 API 失敗、使用者不需要額外提示——達到就可以停。沒有「完美」的技能。

---

**Q：如果測試跑出來結果不穩定怎麼辦？**

A：LLM 本身有隨機性。這就是為什麼建議**「跑 3–5 次同一個請求」**來看結構一致性，而不是看單次輸出。如果 5 次裡有 4 次都對，這個技能可以接受。如果 5 次結果都不同，你的指令太模糊了。

---

**Q：我要怎麼知道是 MCP 問題還是技能問題？**

A：官方推薦的「隔離測試法」：

```
1. 先把技能關掉
2. 直接要求 Claude 用 MCP 做同樣的事
   例：「用 [服務] MCP 幫我取得我的專案」
3. 如果這樣也失敗 → 是 MCP 問題（檢查連線、權限）
4. 如果這樣成功，但加上技能就失敗 → 是技能問題
```

---

**Q：我的技能載入了但 Claude 沒照指令做，怎麼辦？**

A：四種可能，第 5 章會詳細講：
1. 指令太冗長 → 簡化，移到 `references/`
2. 關鍵指令埋太深 → 放到頂端，用 `## Critical` 標示
3. 語言太曖昧 → 改成具體的命令與清單
4. 模型「偷懶」→ 加上明確鼓勵（注意：這招放在 user prompt 比放在 SKILL.md 有效）
