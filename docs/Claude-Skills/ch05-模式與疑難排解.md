### 🛒 **先選路徑**：Problem-first vs. Tool-first

在進入五大模式前，你要先搞清楚你的技能是**哪一種思維**。

**官方用 Home Depot（家得寶）類比：**

```
┌─────────────────────────────────────────────────────┐
│                                                      │
│  你走進 Home Depot，有兩種可能：                       │
│                                                      │
│  🅰️ 「我家廚房櫃子壞了，幫我修」                       │
│     → 店員帶你去拿「合適的工具」                       │
│     → 這是 Problem-first（以問題為起點）               │
│                                                      │
│  🅱️ 「我剛買了一把新電鑽，怎麼用在我的工作上？」         │
│     → 店員教你「怎麼發揮這把鑽頭的最大價值」            │
│     → 這是 Tool-first（以工具為起點）                  │
│                                                      │
└─────────────────────────────────────────────────────┘
```

---

#### 🎭 兩種思維的對照

```
┌──────────────────────────────────────────────────┐
│                                                   │
│  Problem-first                                    │
│  ────────────                                     │
│                                                   │
│  使用者說：「我需要設定一個專案工作區」              │
│                                                   │
│  → 你的技能「自動編排」正確的 MCP 呼叫順序           │
│  → 使用者描述「想要的結果」                          │
│  → 技能搞定所有工具細節                             │
│                                                   │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│                                                   │
│  Tool-first                                       │
│  ─────────                                        │
│                                                   │
│  使用者說：「我已經連上 Notion MCP 了」              │
│                                                   │
│  → 你的技能教 Claude「最佳實踐工作流」               │
│  → 使用者有工具存取權                               │
│  → 技能提供專業知識                                 │
│                                                   │
└──────────────────────────────────────────────────┘
```

**大部分技能會偏向其中一邊。先搞清楚你的定位，再挑模式。**

### 🎯 Pattern 1：順序工作流協調（Sequential Workflow Orchestration）

**什麼時候用？**
> 使用者需要「按特定順序」執行的多步驟流程。

**經典情境**：客戶 onboarding、CI/CD 流水線、多階段部署。

---

#### 📋 標準結構範例：客戶 onboarding

```markdown
# Workflow: Onboard New Customer

## Step 1: Create Account
呼叫 MCP 工具：`create_customer`
參數：name, email, company

## Step 2: Setup Payment
呼叫 MCP 工具：`setup_payment_method`
等待：付款方式驗證完成

## Step 3: Create Subscription
呼叫 MCP 工具：`create_subscription`
參數：plan_id, customer_id（來自 Step 1）

## Step 4: Send Welcome Email
呼叫 MCP 工具：`send_email`
範本：welcome_email_template
```

---

#### 🔑 關鍵技法

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 明確的步驟順序                                 ║
║     → 用 ## Step 1, ## Step 2 清楚編號            ║
║                                                   ║
║  ✅ 步驟間的相依性                                 ║
║     → 說清楚「Step 3 需要 Step 1 的 customer_id」 ║
║                                                   ║
║  ✅ 每個階段的驗證                                 ║
║     → 「等待：付款方式驗證完成」                    ║
║                                                   ║
║  ✅ 失敗時的回滾指令                               ║
║     → 如果 Step 3 失敗，要不要撤銷 Step 1、2？    ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 🗺️ 視覺化流程

```
    ┌──────────────┐
    │   Step 1     │
    │ Create       │
    │ Account      │
    └──────┬───────┘
           │ 傳遞 customer_id
           ▼
    ┌──────────────┐
    │   Step 2     │         ✅ 驗證通過才往下
    │ Setup        ├─────────
    │ Payment      │         ❌ 失敗：回滾 Step 1
    └──────┬───────┘
           │ 傳遞 payment_id
           ▼
    ┌──────────────┐
    │   Step 3     │
    │ Create       │
    │ Subscription │
    └──────┬───────┘
           │
           ▼
    ┌──────────────┐
    │   Step 4     │
    │ Send Welcome │
    │ Email        │
    └──────────────┘
```

#### 💼 Aaron 情境實戰：Hugo 網站遷移技能

你的 WordPress → Hugo 遷移流程，就是一個典型的 Sequential Workflow：

```markdown
# Workflow: WordPress to Hugo Migration

## Step 1: Export WordPress Content
執行：`python scripts/export_wp.py --site {url}`
輸出：wp-export.xml

## Step 2: Validate Export
執行：`python scripts/validate_export.py wp-export.xml`
若失敗：提示使用者檢查 WordPress 權限

## Step 3: Convert to Markdown
執行：`python scripts/wp_to_md.py wp-export.xml`
規則：
- 保留 YAML 前言
- 處理 WordPress shortcodes（參考 references/shortcode-map.md）

## Step 4: Download Images
執行：`python scripts/download_images.py`
重寫所有圖片路徑為本地路徑

## Step 5: Apply MIDA Theme Structure
套用 MIDA Theme 的 content/ 目錄結構

## Step 6: Generate Redirects
產出 301 重導向對照表（舊 URL → 新 URL）

## Step 7: Build Verification
執行：`hugo --buildDrafts` 確認能成功建置
```

### 🎯 Pattern 2：Multi-MCP 協調

**什麼時候用？**
> 工作流程**跨多個服務**。

**經典情境**：設計交接、跨系統資料同步、全通路發佈。

---

#### 📋 標準結構範例：設計到開發的交接

```markdown
# Phase 1: Design Export (Figma MCP)
1. 從 Figma 匯出設計資產
2. 產生設計規格
3. 建立資產清單

# Phase 2: Asset Storage (Drive MCP)
1. 在 Drive 建立專案資料夾
2. 上傳所有資產
3. 產生可分享連結

# Phase 3: Task Creation (Linear MCP)
1. 建立開發任務
2. 在任務中附上資產連結
3. 指派給工程團隊

# Phase 4: Notification (Slack MCP)
1. 在 #engineering 頻道發佈交接摘要
2. 包含資產連結與任務參照
```

---

#### 🔑 關鍵技法

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 階段清楚分開                                   ║
║     → Phase 1, Phase 2... 而不是混在一起         ║
║                                                   ║
║  ✅ MCP 之間的資料傳遞                             ║
║     → Phase 2 要用 Phase 1 產出的「資產清單」     ║
║                                                   ║
║  ✅ 進入下一階段前驗證                             ║
║     → Drive 真的建立好了，才開始建 Linear 任務     ║
║                                                   ║
║  ✅ 集中式錯誤處理                                 ║
║     → 任何階段失敗，通知機制要一致                  ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 🗺️ 視覺化流程

```
        Phase 1                 Phase 2
     ┌───────────┐          ┌───────────┐
     │  Figma    │          │  Drive    │
     │   MCP     │─────────▶│   MCP     │
     └───────────┘  資產清單 └─────┬─────┘
                                   │ 可分享連結
                                   ▼
                             ┌───────────┐
                             │  Linear   │
                             │   MCP     │
                             └─────┬─────┘
                                   │ 任務連結
                                   ▼
                             ┌───────────┐
                             │  Slack    │
                             │   MCP     │
                             └───────────┘
                                 Phase 4
```

### 🎯 Pattern 3：迭代優化（Iterative Refinement）

**什麼時候用？**
> 輸出品質需要「反覆改善」才會變好。

**經典情境**：報告產生、論文寫作、程式碼審查、設計稿修訂。

---

#### 📋 標準結構範例：報告產生

```markdown
# 迭代報告建立

## 初稿
1. 透過 MCP 擷取資料
2. 產生第一版報告草稿
3. 儲存到暫存檔

## 品質檢查
1. 執行驗證腳本：`scripts/check_report.py`
2. 識別問題：
   - 章節缺漏
   - 格式不一致
   - 資料驗證錯誤

## 優化迴圈
1. 逐一處理發現的問題
2. 重新產生受影響的章節
3. 重新驗證
4. 重複，直到達到品質門檻

## 收尾
1. 套用最終格式
2. 產生摘要
3. 儲存最終版
```

---

#### 🔑 關鍵技法

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 明確的品質標準                                 ║
║     → 不是「看起來 OK 就好」                       ║
║     → 是「通過 check_report.py 所有檢查」         ║
║                                                   ║
║  ✅ 迭代改進                                       ║
║     → 每次優化只處理特定問題                        ║
║                                                   ║
║  ✅ 用「驗證腳本」而非「語言指令」                  ║
║     → 程式是確定的，語言詮釋不是                    ║
║                                                   ║
║  ✅ 知道何時停止                                   ║
║     → 設定最大迭代次數（例：最多 3 輪）             ║
║     → 或品質門檻達標就停                           ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 🗺️ 視覺化流程

```
         ┌─────────────┐
         │   初稿生成   │
         └──────┬──────┘
                │
                ▼
         ┌─────────────┐
         │   品質檢查   │◀─────┐
         │ (驗證腳本)   │       │
         └──────┬──────┘       │
                │               │
         ┌──────┴──────┐       │
         │              │       │
         ▼ 有問題        ▼ 通過  │
    ┌──────────┐    ┌──────────┐
    │  優化    │    │  收尾    │
    │  特定章節 │────┘          │
    └──────────┘                ▼
                           ┌─────────┐
                           │  完成   │
                           └─────────┘
```

---

#### 🌟 為什麼這個模式特別重要？

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  💡 Anthropic 的洞見：                             ║
║                                                   ║
║    LLM 的「生成」會有隨機性，                      ║
║    但「驗證腳本」是確定性的。                        ║
║                                                   ║
║    把確定性的部分交給程式，                         ║
║    把創造性的部分交給 Claude，                      ║
║                                                   ║
║    這就是「迭代優化」的威力。                        ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

#### 💼 Aaron 情境實戰：Head First 風格教材產出

```markdown
# 迭代 Head First 教材生成

## 初稿生成
1. 根據主題大綱產生第一版教材
2. 儲存到 /tmp/draft.md

## 品質檢查（scripts/check_headfirst.py）
檢查項目：
- ☐ 有「開場戲劇化場景」嗎？
- ☐ 有「沒有蠢問題」Q&A 區塊嗎？
- ☐ 有「削尖你的鉛筆」練習嗎？
- ☐ 每章有「重點彙整」嗎？
- ☐ 對話框與 ASCII 圖表充足嗎？
- ☐ 段落長度是否符合「短段落原則」？

## 優化迴圈（最多 3 輪）
For each missing element:
  1. 針對缺失的元素補強
  2. 重新執行 check_headfirst.py
  3. 通過 → 進入收尾；沒通過 → 再改

## 收尾
1. 統一排版
2. 產生目錄
3. 輸出最終版 Markdown
```

### 🎯 Pattern 4：情境感知工具選擇（Context-aware Tool Selection）

**什麼時候用？**
> 同樣的目標，但要根據「情境」選不同的工具。

**經典情境**：檔案儲存、通知路由、模型選擇。

---

#### 📋 標準結構範例：智慧檔案儲存

```markdown
# Smart File Storage

## 決策樹
1. 檢查檔案類型與大小
2. 決定最佳儲存位置：
   - 大檔案（>10MB）：用雲端儲存 MCP
   - 協作文件：用 Notion/Docs MCP
   - 程式碼：用 GitHub MCP
   - 暫存檔：用本地儲存

## 執行儲存
根據決策：
- 呼叫對應的 MCP 工具
- 套用服務特定的 metadata
- 產生存取連結

## 向使用者說明
解釋為什麼選擇了這個儲存位置
```

---

#### 🔑 關鍵技法

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 清楚的決策標準                                 ║
║     → 不是「看情況」，而是「> 10MB 就走 A 路徑」   ║
║                                                   ║
║  ✅ 後備選項（Fallback）                           ║
║     → 主選項失敗時的備案                           ║
║                                                   ║
║  ✅ 透明化選擇原因                                 ║
║     → 告訴使用者「為什麼選這個」                    ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 🗺️ 視覺化決策流程

```
        使用者要儲存檔案
              │
              ▼
       ┌─────────────┐
       │  檔案 > 10MB? │
       └──────┬──────┘
              │
     ┌────────┼────────┐
     │                  │
     ▼ 是               ▼ 否
  雲端儲存         ┌─────────────┐
                   │ 檔案類型？    │
                   └──────┬──────┘
                          │
           ┌──────────────┼──────────────┐
           │              │              │
           ▼ 程式碼        ▼ 協作文件     ▼ 暫存
         GitHub         Notion/Docs    本地儲存
```

### 🎯 Pattern 5：領域特定智能（Domain-specific Intelligence）

**什麼時候用？**
> 你的技能不只是「呼叫工具」，還要嵌入「專業知識」。

**經典情境**：金融合規、醫療診斷、法律審查、教育倫理。

---

#### 📋 標準結構範例：付款處理 + 合規檢查

```markdown
# Payment Processing with Compliance

## 處理前（合規檢查）
1. 透過 MCP 擷取交易細節
2. 套用合規規則：
   - 檢查制裁名單
   - 驗證司法管轄區許可
   - 評估風險等級
3. 記錄合規決策

## 處理階段
IF 合規通過：
 - 呼叫付款處理 MCP 工具
 - 套用適當的詐騙檢查
 - 處理交易
ELSE:
 - 標記待審查
 - 建立合規案件

## 稽核軌跡
- 記錄所有合規檢查
- 記錄處理決策
- 產生稽核報告
```

---

#### 🔑 關鍵技法

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  ✅ 把領域專業嵌入邏輯                             ║
║     → 不只是「呼叫 payment API」                   ║
║     → 是「呼叫前先檢查制裁名單」                    ║
║                                                   ║
║  ✅ 合規先於行動                                   ║
║     → 先驗證，再執行                               ║
║                                                   ║
║  ✅ 完整的文件化                                   ║
║     → 每個決策都要能追溯                           ║
║                                                   ║
║  ✅ 清楚的治理                                     ║
║     → 誰有權覆寫？什麼情況要人工審查？              ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 💼 Aaron 情境實戰：投資教育內容發佈 + 合規檢查

```markdown
# 投資教育內容發佈（含合規守門）

## 處理前（合規檢查）
1. 透過 MCP 擷取內容主題
2. 套用金融內容合規規則（references/investment-compliance.md）：
   - 是否包含保證獲利或誇大績效的敘述？
   - 是否混淆投資教育與個別投資建議？
   - 是否揭露風險、資料來源與適用限制？
   - 是否符合台灣金融廣告與投資顧問相關規範？
3. 記錄合規決策與依據

## 發佈階段
IF 合規檢查通過：
 - 產出教育性內容（風險中立口吻）
 - 加上「本內容不構成投資建議」免責聲明
 - 附上原始資料來源
 - 發佈到指定平台
ELSE:
 - 標記待人工審閱
 - 說明具體合規疑慮
 - 建議改寫方向

## 稽核軌跡
- 記錄每次內容的合規審查紀錄
- 保留原始資料來源
- 產生可公開查閱的風險揭露清單
```

**這就是 Pattern 5 的威力**：不只是產出內容，還把**領域智慧**嵌入每個決策。

### 🐛 類別 1：技能無法上傳

---

#### 🚨 症狀 A：「Could not find SKILL.md in uploaded folder」

**原因**：檔名不是**精確的** `SKILL.md`

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  🔍 自我診斷                                       ║
║                                                   ║
║  在 terminal 裡跑：                                 ║
║    ls -la                                         ║
║                                                   ║
║  應該看到：                                         ║
║    ✅ SKILL.md                                    ║
║                                                   ║
║  不能是：                                           ║
║    ❌ skill.md                                    ║
║    ❌ SKILL.MD                                    ║
║    ❌ Skill.md                                    ║
║    ❌ SKILL.markdown                              ║
║                                                   ║
║  解法：重新命名                                     ║
║    mv skill.md SKILL.md                          ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

#### 🚨 症狀 B：「Invalid frontmatter」

**原因**：YAML 格式錯誤

**常見錯誤 1：缺少分隔符**

```yaml
# ❌ 錯誤（沒有 ---）
name: my-skill
description: Does things

# ✅ 正確
---
name: my-skill
description: Does things
---
```

---

**常見錯誤 2：引號沒閉合**

```yaml
# ❌ 錯誤（引號沒結束）
---
name: my-skill
description: "Does things
---

# ✅ 正確
---
name: my-skill
description: "Does things"
---

# ✅ 也正確（沒用引號）
---
name: my-skill
description: Does things
---
```

---

**常見錯誤 3：冒號後沒空格**

```yaml
# ❌ 錯誤
---
name:my-skill
---

# ✅ 正確（冒號後要有空格）
---
name: my-skill
---
```

---

#### 🚨 症狀 C：「Invalid skill name」

**原因**：名稱格式不符

```yaml
# ❌ 錯誤 - 有空格
name: My Cool Skill

# ❌ 錯誤 - 有大寫
name: MyCoolSkill

# ❌ 錯誤 - 有底線
name: my_cool_skill

# ❌ 錯誤 - 使用保留字
name: claude-helper
name: anthropic-tool

# ✅ 正確
name: my-cool-skill
```

---

### 🐛 類別 2：技能不觸發

**症狀**：技能永遠不會自動載入

**這是最常見、也最折磨人的問題。**

---

#### 🔍 修復方法：重寫 description

回去看第 2 章的**description 魔法公式**，重新檢查你的描述。

**快速檢核表：**

```
☐ 描述太籠統嗎？
   「協助處理專案」← 這種不會動

☐ 有沒有使用者真正會說的觸發短語？
   「規劃 sprint」、「建立任務」、「onboard 客戶」

☐ 如果相關，有沒有提到檔案類型？
   「.fig 檔案」、「.csv 檔案」、「WordPress 匯出的 XML」
```

---

#### 🎯 官方除錯神招：問 Claude 自己

```
直接問 Claude：

「你什麼時候會使用 [技能名稱] 這個技能？」

Claude 會把描述引用回來給你。
根據它「抓不到的重點」來調整描述。
```

**實戰示範：**

```
你：    「你什麼時候會使用 hugo-migrator 技能？」

Claude：「我會在使用者提到 Hugo 遷移時使用……」

你：    「那如果使用者說『把部落格搬到 Hugo』呢？」

Claude：「……這個我可能不會主動觸發。」

→ 你的 description 需要補上「搬家」「搬到」等口語詞
```

---

### 🐛 類別 3：技能過度觸發

**症狀**：技能在不相關的查詢中也載入

**這會干擾使用者，讓他們最後乾脆把技能關掉。**

---

#### 🛠️ 三招修復

---

##### 招式 1：加負向觸發

```yaml
# 🟢 改前（太寬鬆）
description: CSV 資料分析

# 🟢 改後（加負向觸發）
description: CSV 檔案的進階資料分析。
  用於統計建模、迴歸、分群。
  【不要】用於簡單的資料探索（那是 data-viz 技能的工作）。
```

---

##### 招式 2：更具體

```yaml
# ❌ 太廣
description: 處理文件

# ✅ 具體
description: 處理 PDF 法律文件以進行合約審查
```

---

##### 招式 3：明確限定範圍

```yaml
# ✅ 清楚限定領域
description: PayFlow 電商付款處理。
  專門用於「線上付款工作流」，
  【不適用於】一般財務查詢。
```

---

### 🐛 類別 4：MCP 連線問題

**症狀**：技能載入成功，但 MCP 呼叫失敗

---

#### 🔍 四步檢查清單

---

##### 步驟 1：確認 MCP 伺服器連線狀態

```
▸ Claude.ai：Settings > Extensions > [你的服務]
▸ 應該顯示「Connected」
```

---

##### 步驟 2：檢查認證

```
☐ API key 有效，沒過期
☐ 有正確的權限 / scope
☐ OAuth token 已重新整理
```

---

##### 步驟 3：隔離測試 MCP（超重要！）

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  🧪 關鍵技巧：把技能關掉，直接測 MCP                ║
║                                                   ║
║  請 Claude：                                       ║
║    「用 [服務] MCP 幫我取得我的專案」               ║
║                                                   ║
║  ✅ 如果這樣就失敗                                 ║
║     → 問題在 MCP，不是技能                         ║
║     → 檢查連線、權限、伺服器狀態                    ║
║                                                   ║
║  ✅ 如果這樣成功，但加上技能就失敗                  ║
║     → 問題在技能                                   ║
║     → 下一步：檢查工具名稱                          ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

---

##### 步驟 4：驗證工具名稱

```
☐ 技能引用的 MCP 工具名稱正確
☐ 對照 MCP 伺服器文件
☐ 工具名稱「區分大小寫」！
```

**實戰範例：**

```markdown
# ❌ 錯誤（工具名打錯）
呼叫 MCP 工具：`Create_Customer`

# ✅ 正確
呼叫 MCP 工具：`create_customer`
```

### 🐛 類別 5：指令沒被遵循

**症狀**：技能載入了，但 Claude 沒照著做

**這是最難診斷的問題，因為從外表看技能「好像有在運作」。**

---

#### 🔍 四種常見原因

---

##### 原因 1：指令太冗長

```
🔴 問題：SKILL.md 有 8,000 字，Claude 讀到一半忘了前面的指令

✅ 解法：
   ▸ 把指令精簡
   ▸ 用條列式、編號
   ▸ 詳細文件搬到 references/
```

---

##### 原因 2：關鍵指令埋太深

```
🔴 問題：重要指令寫在第 50 個項目裡，被淹沒

✅ 解法：
   ▸ 關鍵指令放最頂端
   ▸ 用 ## Important 或 ## Critical 標題強調
   ▸ 重要規則重複提醒
```

**範例：**

```markdown
# My Skill

## ⚠️ CRITICAL - 讀我第一

在執行任何 MCP 呼叫前，先驗證：
- API key 是否存在
- 使用者是否有權限

（其他指令在下面……）
```

---

##### 原因 3：語言太曖昧

```
# ❌ 壞
Make sure to validate things properly.
（驗證什麼？怎麼驗證？什麼叫 properly？）

# ✅ 好
CRITICAL: Before calling create_project, verify:
- Project name is non-empty
- At least one team member assigned
- Start date is not in the past
```

---

##### 💎 **進階技巧**：用腳本代替語言指令

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  📌 官方建議                                       ║
║                                                   ║
║  對於「關鍵驗證」，考慮「打包一個腳本」            ║
║  來程式化地做檢查，                                ║
║  而不是依賴語言指令。                              ║
║                                                   ║
║  ➤ 程式碼是「確定性的」                             ║
║  ➤ 語言詮釋「不是」                                 ║
║                                                   ║
║  範例參考：Office skills (docx, pptx, xlsx)       ║
║  都大量使用這種模式。                              ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

**對比範例：**

```markdown
# 🔴 語言指令版本（不確定）
確認所有任務都有指派負責人。
如果沒有，提示使用者補上。

# 🟢 腳本驗證版本（確定）
執行：`python scripts/validate_assignees.py {project_id}`
如果回傳 non-zero exit code，提示使用者補上缺漏
```

---

##### 原因 4：模型「懶惰」

**這個很微妙，但真實存在。**

```
🔴 症狀：Claude 跳過了某些步驟，特別是耗時的驗證步驟

✅ 解法：加上明確的鼓勵語

「# Performance Notes
- Take your time to do this thoroughly
- Quality is more important than speed
- Do not skip validation steps」
```

---

#### 💡 **超重要提醒**

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  📣 注意！                                         ║
║                                                   ║
║  「模型懶惰」的提醒語，                             ║
║  放在「使用者 prompt」比放在「SKILL.md」有效。      ║
║                                                   ║
║  但如果要放在技能裡，                              ║
║  請放在 SKILL.md 最頂端，                         ║
║  用 ## Critical 標示。                            ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

### 🐛 類別 6：大型上下文造成效能問題

**症狀**：技能變慢、回應品質下降

---

#### 🔍 三個可能原因

```
🔴 可能原因：
  1. 技能內容太大
  2. 同時啟用太多技能
  3. 全部內容都載入了，沒用漸進式揭露
```

---

#### 🛠️ 解法 1：優化 SKILL.md 大小

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  📏 硬性建議                                       ║
║                                                   ║
║  ▸ SKILL.md 控制在 5,000 字以內                    ║
║  ▸ 詳細文件搬到 references/                       ║
║  ▸ 在 SKILL.md 裡用「連結」引用，不要「內嵌」      ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

**判斷流程：**

```
              這段內容要放哪？
                    │
                    ▼
         ┌─────────────────────┐
         │ Claude 每次都需要看到？│
         └──────────┬──────────┘
                    │
           ┌────────┴────────┐
           │                  │
           ▼ 是               ▼ 否
      SKILL.md            references/
      （核心指令）         （按需載入）
```

---

#### 🛠️ 解法 2：減少同時啟用的技能

```
╔══════════════════════════════════════════════════╗
║                                                   ║
║  📊 官方指引                                       ║
║                                                   ║
║  ▸ 如果同時啟用 20-50 個以上的技能，               ║
║    評估一下是否真的都需要                           ║
║                                                   ║
║  ▸ 建議「選擇性啟用」                               ║
║                                                   ║
║  ▸ 可以考慮做「技能包」                             ║
║    把相關的能力打包，使用者一次啟用一包             ║
║                                                   ║
╚══════════════════════════════════════════════════╝
```

### 🧯 **沒有蠢問題**

**Q：我的技能時好時壞，一下觸發一下不觸發，怎麼回事？**

A：這通常是 description 寫得「邊緣」——在 Claude 的判斷門檻上下游走。解法是讓 description 更明確地指向「這情境一定用我」的信號。

---

**Q：我同時打開 30 個技能，Claude 會搞混嗎？**

A：30 個還算 OK，官方說超過 20-50 個就要注意。如果你發現觸發混亂，優先關掉「description 寫得不夠精準」的那些技能。

---

**Q：用腳本做驗證，感覺很麻煩。什麼時候值得這樣做？**

A：三個時機：
1. **關鍵驗證**（錯了會造成嚴重後果）
2. **需要精確計算**（例如檔案大小、金額、日期比較）
3. **需要「每次結果都一樣」**（例如格式檢查）

如果是「一般的理解或判斷」，語言指令就夠了。

---

**Q：我把 SKILL.md 移到 references/ 了，結果 Claude 反而不會自動去讀，怎麼辦？**

A：這是經典錯誤！`references/` 不會自動載入，Claude 要**被明確指引**去讀。在 SKILL.md 裡寫清楚：

```markdown
處理 API 錯誤前，先查閱 `references/api-errors.md` 了解：
- 常見錯誤碼
- 重試策略
- 降級處理
```

Claude 看到這段才會去讀那個檔案。

---

**Q：我同事用我的技能結果壞掉了，但我自己跑都好好的，為什麼？**

A：最常見原因：**環境差異**。
- MCP 連線不同
- API key 權限不同
- 作業系統（Windows/Mac/Linux）
- Python 版本

**解法**：在 YAML 前言加 `compatibility`，列出所有環境需求。
