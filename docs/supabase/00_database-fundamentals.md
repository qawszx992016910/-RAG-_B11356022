# Head First 資料庫入門 — 從混亂到秩序

> **"好的資料庫設計，就像好的收納術——東西放對位置，找東西才快。"**

你是不是也有過這種經驗？打開一份 Excel，裡面有 30 個欄位、5000 行，光是找一筆客戶的電話就要滾半天。

改一個客戶地址，要改 87 行。漏改了 3 行，然後老闆問你：「欸，這個客戶到底住哪裡？」

## Part 1: 為什麼你的試算表會爆炸

### 問題場景

小美開了一間網路商店，用 Excel 管訂單。她的表長這樣：

```
┌──────────┬──────────┬────────────┬──────────┬──────────┬────────┬──────┬──────┐
│ order_id │ customer │ phone      │ address  │ product  │ price  │ qty  │ date │
├──────────┼──────────┼────────────┼──────────┼──────────┼────────┼──────┼──────┤
│ 001      │ 王大明   │ 0912-xxx   │ 台北市   │ 藍牙耳機 │ 1,200  │  1   │ 3/01 │
│ 002      │ 王大明   │ 0912-xxx   │ 台北市   │ 手機殼   │   350  │  2   │ 3/01 │
│ 003      │ 李小華   │ 0933-yyy   │ 台中市   │ 藍牙耳機 │ 1,200  │  1   │ 3/02 │
│ 004      │ 王大明   │ 0912-xxx   │ 台北市   │ 充電線   │   199  │  3   │ 3/05 │
│ 005      │ 張三     │ 0955-zzz   │ 高雄市   │ 手機殼   │   350  │  1   │ 3/06 │
│ 006      │ 王大明   │ 0978-NEW   │ 新北市   │ 螢幕貼   │   299  │  1   │ 3/07 │
└──────────┴──────────┴────────────┴──────────┴──────────┴────────┴──────┴──────┘
```

> **腦筋急轉彎**：這份表有什麼問題？在往下看之前，先花 30 秒自己找找看。
>
> 提示：看看王大明的資料。

找到了嗎？

### 問題一：更新異常 (Update Anomaly)

王大明換了新電話 `0978-NEW`，但只有第 6 筆訂單更新了。前面 3 筆還是舊號碼。

現在你要查王大明的電話——到底是 `0912-xxx` 還是 `0978-NEW`？

**這就是更新異常**：同一份資訊存在多個地方，更新時只改了部分，造成資料不一致。

想像一下：如果王大明有 500 筆訂單，你要改 500 行。漏改 1 行，就炸了。

### 問題二：新增異常 (Insert Anomaly)

新客戶「趙六」打電話來問商品，你想先把他的聯絡資料存起來。

但你做不到——因為這張表的每一行都需要 `order_id`、`product`、`price`。沒有訂單，就沒辦法新增客戶。

**這就是新增異常**：表的結構迫使你「必須有 A 才能存 B」，即使 A 和 B 其實是獨立的事情。

### 問題三：刪除異常 (Delete Anomaly)

李小華只有一筆訂單（第 3 行）。如果她要求退貨，你刪掉這行——

李小華的電話、地址，全部消失了。

**這就是刪除異常**：刪除一個事實（訂單），意外地刪掉了另一個事實（客戶資料）。

### 問題四：資料不一致

再看一次王大明。第 1-4 行地址是「台北市」，第 6 行變成「新北市」。

是他搬家了？還是打錯了？你不知道。因為**同一份資料存在太多地方**，沒有一個「唯一真相來源」(Single Source of Truth)。

### 根本原因

```
問題根源：把不同的「事情」混在同一張表裡

┌─────────────────────────────────────────────────┐
│              一張大表（什麼都有）                  │
│                                                  │
│  顧客資料 + 商品資料 + 訂單資料 = 💥 爆炸        │
└─────────────────────────────────────────────────┘

                    ↓ 解法 ↓

┌──────────┐    ┌──────────┐    ┌──────────────┐
│ customers │    │ products │    │   orders     │
│          │    │          │    │ + order_items │
│ 王大明    │    │ 藍牙耳機 │    │ 誰買了什麼   │
│ 電話×1   │    │ 價格×1   │    │ 參照兩邊     │
└──────────┘    └──────────┘    └──────────────┘
    唯一真相         唯一真相          關聯連結
```

> **Head First 原則**：每一個「事實」只存在一個地方。需要的時候用關聯（JOIN）去找，而不是到處複製貼上。

這就是為什麼我們需要——**正規化**。

## Part 2: 正規化 — 資料的斷捨離

正規化就是一套規則，幫你把「什麼都塞在一起」的表，拆成乾淨、沒有冗餘的結構。

就像收納術：不是把所有東西丟進同一個抽屜，而是分類放好。

### 第一正規化 (1NF) — 每格只放一件事

**規則**：消除重複群組，每個儲存格只有**原子值**（atomic value）。

#### 問題場景

```
┌────────┬─────────────────┬────────────────────┐
│ doc_id │ title           │ tags               │
├────────┼─────────────────┼────────────────────┤
│ 001    │ AI 入門         │ 科技,AI,入門        │
│ 002    │ 股市分析        │ 財經,投資           │
│ 003    │ 遊戲評測        │ 娛樂,科技,遊戲      │
└────────┴─────────────────┴────────────────────┘
```

`tags` 欄位塞了多個值，用逗號分隔。

> **腦筋急轉彎**：如果你要找出所有有「科技」標籤的文章，SQL 要怎麼寫？
>
> `WHERE tags = '科技'`？不行，只能找到「剛好只有科技」的。
> `WHERE tags LIKE '%科技%'`？會把「非科技」也找出來。而且效能超差——資料庫不能用 index。

#### 解法：拆成獨立的行

```
┌────────┬─────────────────┬────────┐
│ doc_id │ title           │ tag    │
├────────┼─────────────────┼────────┤
│ 001    │ AI 入門         │ 科技   │
│ 001    │ AI 入門         │ AI     │
│ 001    │ AI 入門         │ 入門   │
│ 002    │ 股市分析        │ 財經   │
│ 002    │ 股市分析        │ 投資   │
│ 003    │ 遊戲評測        │ 娛樂   │
│ 003    │ 遊戲評測        │ 科技   │
│ 003    │ 遊戲評測        │ 遊戲   │
└────────┴─────────────────┴────────┘
```

現在 `WHERE tag = '科技'` 就能精準找到。但——`title` 重複了很多次。別急，2NF 會處理。

#### 1NF 記憶口訣

> **每格一值，每行唯一。**

- [x] 沒有用逗號分隔的多值欄位
- [x] 沒有「陣列式」的重複欄位（like `tag1`, `tag2`, `tag3`）
- [x] 每一行都能被唯一識別

---

### 第二正規化 (2NF) — 別讓不相干的東西黏在一起

**前提**：已滿足 1NF。

**規則**：消除**部分相依**（Partial Dependency）。非鍵欄位必須完全依賴整個主鍵，不能只依賴主鍵的一部分。

#### 問題場景

小美的訂單明細表，主鍵是 `(order_id, product_id)`：

```
┌──────────┬────────────┬──────────────┬────────┬─────┐
│ order_id │ product_id │ product_name │ price  │ qty │
├──────────┼────────────┼──────────────┼────────┼─────┤
│ 001      │ P01        │ 藍牙耳機     │ 1,200  │  1  │
│ 001      │ P02        │ 手機殼       │   350  │  2  │
│ 002      │ P01        │ 藍牙耳機     │ 1,200  │  1  │
│ 003      │ P02        │ 手機殼       │   350  │  1  │
└──────────┴────────────┴──────────────┴────────┴─────┘
```

`product_name` 和 `price` 只依賴 `product_id`，跟 `order_id` 完全無關。

這就是**部分相依**——非鍵欄位只依賴複合主鍵的一部分。

> **你的大腦在想**：「所以如果藍牙耳機漲價了，我要改兩行？」
>
> 沒錯。而且如果有 1000 筆訂單買了藍牙耳機，你要改 1000 行。更新異常又來了。

#### 解法：拆出 products 表

```
products 表                      order_items 表
┌────────────┬──────────┬───────┐ ┌──────────┬────────────┬─────┐
│ product_id │ name     │ price │ │ order_id │ product_id │ qty │
├────────────┼──────────┼───────┤ ├──────────┼────────────┼─────┤
│ P01        │ 藍牙耳機 │ 1,200 │ │ 001      │ P01        │  1  │
│ P02        │ 手機殼   │   350 │ │ 001      │ P02        │  2  │
└────────────┴──────────┴───────┘ │ 002      │ P01        │  1  │
                                  │ 003      │ P02        │  1  │
                                  └──────────┴────────────┴─────┘
```

藍牙耳機的名稱和價格只存一次。要改？改一個地方就好。

#### 2NF 記憶口訣

> **全靠主鍵，不靠半鍵。**

- [x] 已滿足 1NF
- [x] 每個非鍵欄位都依賴**完整的**主鍵
- [x] 如果只依賴主鍵的一部分 → 拆出去

---

### 第三正規化 (3NF) — 只跟主鍵說話

**前提**：已滿足 2NF。

**規則**：消除**遞移相依**（Transitive Dependency）。非鍵欄位不能透過另一個非鍵欄位來依賴主鍵。

#### 問題場景

```
orders 表
┌──────────┬─────────────┬───────────────┬───────────────┐
│ order_id │ customer_id │ customer_name │ customer_city │
├──────────┼─────────────┼───────────────┼───────────────┤
│ 001      │ C01         │ 王大明        │ 台北市        │
│ 002      │ C02         │ 李小華        │ 台中市        │
│ 003      │ C01         │ 王大明        │ 台北市        │
└──────────┴─────────────┴───────────────┴───────────────┘
```

`customer_name` 和 `customer_city` 依賴 `customer_id`，而 `customer_id` 又依賴 `order_id`。

這就是**遞移相依**：`order_id → customer_id → customer_name`。

`customer_name` 並不直接依賴 `order_id`，它是透過 `customer_id` 間接依賴的。

> **腦筋急轉彎**：如果王大明從台北搬到新北，你要改幾行？答案是——看他有幾筆訂單。又是更新異常。

#### 解法：拆出 customers 表

```
customers 表                     orders 表
┌─────────────┬──────────┬───────┐ ┌──────────┬─────────────┐
│ customer_id │ name     │ city  │ │ order_id │ customer_id │
├─────────────┼──────────┼───────┤ ├──────────┼─────────────┤
│ C01         │ 王大明   │ 台北市│ │ 001      │ C01         │
│ C02         │ 李小華   │ 台中市│ │ 002      │ C02         │
└─────────────┴──────────┴───────┘ │ 003      │ C01         │
                                   └──────────┴─────────────┘
```

現在王大明搬家，改 `customers` 表的一行就好。乾淨。

#### 最終乾淨設計：三表分離

```
┌─────────────┐     ┌──────────────┐     ┌────────────┐
│  customers  │     │    orders    │     │  products  │
├─────────────┤     ├──────────────┤     ├────────────┤
│ customer_id │◄────│ customer_id  │     │ product_id │
│ name        │     │ order_id     │     │ name       │
│ phone       │     │ date         │     │ price      │
│ city        │     └──────┬───────┘     └─────┬──────┘
└─────────────┘            │                   │
                    ┌──────▼───────────────────▼──────┐
                    │          order_items             │
                    ├─────────────────────────────────┤
                    │ order_id (FK)                    │
                    │ product_id (FK)                  │
                    │ qty                              │
                    └─────────────────────────────────┘
```

每個「事實」只存一次。需要組合資訊的時候，用 `JOIN`。

#### 3NF 記憶口訣

> **只靠主鍵，不靠中間人。**

- [x] 已滿足 2NF
- [x] 沒有非鍵欄位透過另一個非鍵欄位間接依賴主鍵
- [x] 所有非鍵欄位直接依賴主鍵

---

### BCNF — 學者的潔癖

Boyce-Codd Normal Form (BCNF) 比 3NF 更嚴格一點：要求**每個決定因素都是候選鍵**。

聽起來很抽象？因為在實務上，99% 的情況 3NF = BCNF。只有在出現「非候選鍵決定候選鍵的一部分」這種罕見情況時才會不同。

> **Head First 原則**：考試會考 BCNF，但工作上 3NF 就夠用了。先把 3NF 練到肌肉記憶，BCNF 知道它存在就好。

---

### 正規化總結表

| 正規化等級 | 消除什麼 | 記憶口訣 | 白話文 |
|-----------|---------|---------|--------|
| 1NF | 重複群組 | 每格一值 | 不要在一格裡塞逗號分隔的多個值 |
| 2NF | 部分相依 | 全靠主鍵 | 每個欄位要依賴完整的主鍵，不能只靠半個 |
| 3NF | 遞移相依 | 只靠主鍵 | 欄位不能透過其他非鍵欄位間接依賴主鍵 |
| BCNF | 非候選鍵決定因素 | 學者潔癖 | 3NF 的加強版，實務上很少遇到差異 |

> **腦筋急轉彎**：正規化的三步驟，其實就是在回答同一個問題的不同版本：「這個欄位，到底是誰的責任？」
>
> - 1NF：這個**值**，是不是一件事？
> - 2NF：這個欄位，是不是**整個**主鍵的責任？
> - 3NF：這個欄位，是不是**直接**由主鍵負責？

## Part 3: ER Diagram — 畫出你的資料藍圖

正規化告訴你「怎麼拆」，ER Diagram 告訴你「拆完長什麼樣」。

ER = Entity-Relationship，實體-關係模型。這是在寫任何 SQL 之前，你應該先畫的圖。

### 三個核心概念

| 概念 | 對應 | 怎麼找 | 例子 |
|------|------|--------|------|
| 實體 (Entity) | 表 (Table) | 找名詞 | 顧客、訂單、商品 |
| 屬性 (Attribute) | 欄位 (Column) | 找形容詞 | 姓名、價格、數量 |
| 關係 (Relationship) | 外鍵 (FK) | 找動詞 | 下單、包含、屬於 |

> **你的大腦在想**：「所以我只要把需求裡的名詞、形容詞、動詞分類，就能畫出 ER Diagram？」
>
> 差不多就是這樣。當然實務上會更複雜，但這個思路方向是對的。

### 關係類型

#### 一對一 (1:1)

一個使用者只有一個個人檔案，一個個人檔案只屬於一個使用者。

```
[users] 1────1 [profiles]
```

什麼時候用 1:1？通常是為了把「常用欄位」和「不常用欄位」分開，或是把敏感資料隔離。

```sql
-- users 表：認證用，常查詢
CREATE TABLE users (
  id   TEXT PRIMARY KEY,
  auth_user_id UUID UNIQUE NOT NULL
);

-- profiles 表：個人資料，偶爾查詢
CREATE TABLE profiles (
  user_id  TEXT PRIMARY KEY REFERENCES users(id),
  username TEXT,
  avatar   TEXT,
  bio      TEXT
);
```

#### 一對多 (1:N)

一個顧客可以有多筆訂單，但每筆訂單只屬於一個顧客。

```
[customers] 1────N [orders]
```

這是最常見的關係類型。用外鍵 (FK) 實作——在「多」的那邊加一個欄位指向「一」的那邊：

```sql
CREATE TABLE orders (
  id          TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL REFERENCES customers(id),  -- FK 在「多」的這邊
  order_date  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> **Head First 原則**：外鍵永遠放在「多」的那一邊。記住這條規則，你就不會搞混。

#### 多對多 (M:N)

一筆訂單可以包含多個商品，一個商品可以出現在多筆訂單裡。

```
[orders] N────M [products]
```

**問題來了**：關聯式資料庫沒有辦法直接表達 M:N 關係。

**解法**：加一張**中間表**（junction table / bridge table）。

```
[orders] 1───N [order_items] N───1 [products]
```

```sql
CREATE TABLE order_items (
  id         TEXT PRIMARY KEY,
  order_id   TEXT NOT NULL REFERENCES orders(id),
  product_id TEXT NOT NULL REFERENCES products(id),
  quantity   INTEGER NOT NULL DEFAULT 1,
  UNIQUE(order_id, product_id)  -- 同一筆訂單不會有重複商品
);
```

中間表把一個 M:N 拆成兩個 1:N。這是資料庫設計最基本的技巧之一。

> **腦筋急轉彎**：為什麼不在 orders 表加一個 `product_ids TEXT[]` 陣列欄位就好？
>
> 因為那樣你就沒辦法在中間存 `quantity`（數量）、`unit_price`（成交單價）這些只屬於「這筆訂單中的這個商品」的資訊。中間表不只是連接兩邊，它自己也可以有屬性。

### 實作練習：小型電商 ER Diagram

把前面學到的全部組起來：

```
┌─────────────┐         ┌──────────────┐         ┌────────────┐
│  customers  │         │    orders    │         │  products  │
├─────────────┤         ├──────────────┤         ├────────────┤
│ PK id       │◄──1:N──│ FK customer_ │         │ PK id      │
│    name     │         │ PK id       │         │    name    │
│    phone    │         │    date     │         │    price   │
│    city     │         └──────┬───────┘         └─────┬──────┘
└─────────────┘                │                       │
                               │ 1:N                   │ 1:N
                               │                       │
                        ┌──────▼───────────────────────▼──────┐
                        │            order_items              │
                        ├─────────────────────────────────────┤
                        │ PK id                               │
                        │ FK order_id                         │
                        │ FK product_id                       │
                        │    quantity                         │
                        └─────────────────────────────────────┘
```

四張表、兩個 1:N、一個 M:N（透過中間表實現）。

這就是你在電商 Stage 3 會看到的骨架——只是實際版本有 20 張表而已。

## Part 4: 反正規化 — 知道規則才能打破規則

### 等等，正規化不是越多越好嗎？

理論上是。但現實世界有一個正規化理論沒告訴你的東西：**效能**。

正規化到極致，查一筆訂單的完整資訊可能要 JOIN 5 張表。在高流量的電商網站，這可能太慢了。

所以有時候，我們會**故意**把某些資料冗餘存放——這就是反正規化（Denormalization）。

### 什麼時候該反正規化？

**不是因為懶，而是因為有充分理由。**

#### 場景一：價格快照

```sql
-- 正規化做法：order_items 只存 product_id，要價格就去 JOIN products
-- 問題：商品漲價後，歷史訂單的金額也跟著變了 💥

-- 反正規化做法：下單時把當時的價格「快照」下來
CREATE TABLE order_items (
  id           TEXT PRIMARY KEY,
  order_id     TEXT NOT NULL REFERENCES orders(id),
  product_id   TEXT NOT NULL REFERENCES products(id),
  quantity     INTEGER NOT NULL,
  unit_price   NUMERIC(12,2) NOT NULL,  -- 下單當時的價格快照
  product_name TEXT NOT NULL             -- 下單當時的商品名稱快照
);
```

> **你的大腦在想**：「這不就是違反 3NF 嗎？product_name 依賴 product_id，不是依賴 order_item 的主鍵。」
>
> 沒錯，這就是**有意識的**反正規化。因為這裡的 product_name 代表的是「下單那一刻的商品名稱」，跟 products 表裡的「現在的商品名稱」是不同的事實。

#### 場景二：JSONB 存非結構化資料

```sql
-- AI model 的參數不固定，每個 model 的 metadata 結構都不一樣
CREATE TABLE documents (
  id       TEXT PRIMARY KEY,
  content  TEXT NOT NULL,
  metadata JSONB DEFAULT '{}'::jsonb  -- 彈性結構
);

-- metadata 可能長這樣：
-- {"model": "gpt-4", "tokens": 1500, "temperature": 0.7}
-- {"model": "claude-3", "tokens": 2000, "max_tokens": 4096}
```

每個 model 的參數不同，硬要正規化（為每種 model 建一張表）反而更痛苦。

#### 場景三：計數器快取

```sql
-- 正規化做法：要知道一個 crawl_run 找到幾頁，就 COUNT(*) pages
-- 問題：pages 有 10 萬筆的時候，每次 COUNT 都很慢

-- 反正規化做法：維護一個計數器
CREATE TABLE crawl_runs (
  id           TEXT PRIMARY KEY,
  pages_found  INTEGER NOT NULL DEFAULT 0,  -- 反正規化計數器
  articles_extracted INTEGER NOT NULL DEFAULT 0
);
```

用 trigger 或應用邏輯來維護這個計數器，查詢速度從 O(n) 變成 O(1)。

### 反正規化決策原則

> **正規化是預設。反正規化是有意識的設計決策，不是偷懶。**
>
> 每次反正規化，你都應該能回答：「我為什麼這樣做？代價是什麼？」

代價通常是：

1. **寫入變複雜**：你需要 trigger 或應用邏輯來維護一致性
2. **資料可能不一致**：如果 trigger 出錯或應用程式有 bug
3. **維護成本增加**：改 schema 的時候要多想一步

### 連結到後續 Stage

| 反正規化技巧 | 出現在 | 原因 |
|-------------|-------|------|
| 價格/名稱快照 | 電商 Stage 8 | 下單後商品改名改價不影響歷史訂單 |
| JSONB metadata | RAG Stage 4 | AI model 參數不固定，結構彈性 |
| Snapshot + Journal 雙軌制 | 電商 Stage 6 | 庫存查詢效能 + 異動追蹤 |
| Denormalized counts | 爬蟲 Stage 3 | pages_found, articles_extracted 計數器 |

## Part 5: 資料型別選擇指南

選對資料型別，就像穿對尺寸的鞋——不會太大浪費空間，不會太小擠到痛。

### 主鍵選型：ULID vs UUID vs BIGINT

這個決策你在後面三個 schema（電商 20 表、爬蟲 10 表、RAG 7 表）都會看到。

| | BIGINT (SERIAL) | UUID v4 | ULID |
|---|---|---|---|
| 儲存大小 | 8 bytes | 36 chars | **26 chars** |
| 可排序 | 單機遞增 | 完全隨機 | **按時間排序** |
| B-Tree 效能 | 順序寫入（快） | 隨機寫入（頁分裂） | **順序寫入（快）** |
| 分散式安全 | 需要 sequence（會撞號） | 安全 | **安全** |
| 可讀性 | `42` | `550e8400-e29b-...` | `01HXYZ1234ABCD` |
| 可猜測性 | 高（容易被爬） | 低 | **低** |

> **腦筋急轉彎**：假設你的 API 用 BIGINT 當 user ID——`/api/users/42`。
> 攻擊者只要從 1 開始遞增，就能把所有用戶資料爬走。
> ULID 長這樣：`/api/users/01HXYZ1234ABCDEFGH`——試試看從這裡猜下一個？

**結論**：後面所有 schema 統一使用 ULID 存為 TEXT。理由就是上面這張表。

### 常用型別速查表

| 型別 | 用途 | 範例 | 注意事項 |
|------|------|------|---------|
| `TEXT` | 不限長度字串 | 名稱、描述、URL | PostgreSQL 裡 TEXT 和 VARCHAR 效能相同 |
| `INTEGER` | 整數 (-2B~2B) | 數量、計數 | 超過 21 億就要用 BIGINT |
| `BIGINT` | 大整數 | 超大計數器 | 通常用不到，除非你是 Facebook |
| `NUMERIC(p,s)` | 精確小數 | 金額 `NUMERIC(12,2)` | **金額必須用這個，不能用 FLOAT** |
| `BOOLEAN` | 是/否 | is_active, is_deleted | 只有 true / false / null |
| `TIMESTAMPTZ` | 帶時區時間戳 | created_at, updated_at | **永遠用 TIMESTAMPTZ，不要用 TIMESTAMP** |
| `JSONB` | 半結構化資料 | config, metadata | 可以建 GIN index，查詢效能不錯 |
| `TEXT[]` | 文字陣列 | tags | 但通常**用關聯表更好**（回顧 1NF） |
| `VECTOR(n)` | 向量 | RAG embedding | 需要 pgvector 擴充，RAG Stage 才會用到 |

### 為什麼金額不能用 FLOAT？

> **腦筋急轉彎**：打開 Python，試試這個：
>
> ```python
> >>> 0.1 + 0.2
> 0.30000000000000004
> ```
>
> 驚不驚喜？意不意外？

浮點數（FLOAT / DOUBLE）用二進位表示小數，有些十進位數字**無法精確表示**。

在科學計算裡，0.0000000000000004 的誤差無所謂。但在金融系統裡——

```
客戶下了 10,000 筆小額訂單，每筆 0.1 元
FLOAT 算出來：999.9999999999998 元
NUMERIC 算出來：1000.00 元
```

差了 0.0000000000002 元？沒關係？等你累積一年、一百萬筆交易，誤差就變成帳對不起來。

```sql
-- ❌ 永遠不要這樣做
price FLOAT NOT NULL

-- ✅ 永遠這樣做
price NUMERIC(12,2) NOT NULL  -- 12 位數，小數點後 2 位
```

### 為什麼用 TIMESTAMPTZ 而不是 TIMESTAMP？

```sql
-- TIMESTAMP：存的是「牆上的時鐘」，沒有時區資訊
-- 你在台灣存 '2024-03-25 14:00:00'，美國同事讀到也是 14:00
-- 但那其實是他的凌晨 2 點 💥

-- TIMESTAMPTZ：存的是地球上的一個絕對時間點
-- 不管誰在哪裡讀，都會轉換成他的當地時間
```

> **Head First 原則**：永遠用 `TIMESTAMPTZ`。沒有例外。就算你的系統「現在」只在台灣用，未來可能會擴展。而且 PostgreSQL 裡 TIMESTAMPTZ 和 TIMESTAMP 的儲存空間**完全一樣**——都是 8 bytes。沒有任何理由不用 TIMESTAMPTZ。

## Part 7: 認識 PostgreSQL — 你的資料引擎

觀念打好了。現在來認識你即將使用的工具：**PostgreSQL**——全世界最受歡迎的開源關聯式資料庫，也是 Supabase 的底層引擎。

### PostgreSQL 是什麼？

- 開源關聯式資料庫
- 強型別
- ACID 交易
- 支援 JSONB（同時兼具 NoSQL 能力）
- 支援 Index、View、Trigger、Function
- 支援複雜分析查詢

> **跟 Pandas 比**：Pandas 適合單次分析，但沒有版本管理、多人協作、權限控管、持久化資料模型、API 供應。真實世界的資料科學一定接資料庫。

### 核心概念速覽

前面幾個 Part 教了你「為什麼要這樣設計」，現在看看 PostgreSQL 怎麼實現這些觀念：

#### (A) Table — 你在 Part 2 學的正規化，最終落地在這裡

```sql
CREATE TABLE students (
  id SERIAL PRIMARY KEY,
  name TEXT,
  score NUMERIC,
  created_at TIMESTAMP DEFAULT NOW()
);
```

#### (B) Index — 大數據查詢加速

為什麼資料科學需要 Index？`GROUP BY` / `WHERE` 在百萬筆資料上，有沒有 Index 差十倍。

```sql
CREATE INDEX idx_students_score ON students(score);
```

#### (C) JOIN — Part 3 的 ER Diagram，靠 JOIN 串起來

```sql
SELECT s.name, c.course_name
FROM students s
JOIN enrollments e ON s.id = e.student_id
JOIN courses c ON e.course_id = c.id;
```

#### (D) JSONB — 半結構資料的秘密武器

PostgreSQL 可以存模型輸出、AI metadata、半結構化資料：

```sql
CREATE TABLE predictions (
  id SERIAL,
  model_output JSONB
);
```

這讓 PostgreSQL 同時兼具 NoSQL 能力——你在後面的 RAG Stage 會大量用到。

### PostgreSQL 核心概念對照表

| 概念 | 說明 | 對應本章觀念 | 資料科學應用 |
|------|------|-------------|-------------|
| Table | 結構化資料儲存 | Part 2 正規化 | 取代 CSV |
| Index | 查詢加速 | — | 大資料場景 |
| JOIN | 多表關聯 | Part 3 ER Diagram | 資料整合 |
| JSONB | 半結構資料 | Part 4 反正規化 | 模型輸出、AI metadata |
