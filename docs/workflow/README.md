## 💡 快速參考

### 四句咒語（核心心法）

```
📋 /specify  ── 先說清楚要做什麼
🔍 /clarify  ── 把模糊的地方問清楚
🗺️  /plan    ── 畫一張施工藍圖
🔨 /implement── 按圖施工，步步驗證

記住這四句，你就掌握了 80% 的精髓。
```

### 四問題法（快速評估）

```
Q1: 涉及多少模組？
    □ 1 個 → 0 分  □ 2+ 個 → 2 分

Q2: 有權限、並發或不可逆操作？
    □ 沒有 → 0 分  □ 有 → 3 分

Q3: 涉及 DB Schema 變更？
    □ 不涉及 → 0 分  □ 涉及 → 2 分

Q4: 涉及外部 API 整合？
    □ 不涉及 → 0 分  □ 涉及 → 2 分

總分：____

0-2  → Lite（快、簡單）
3-5  → Standard（平衡、可靠）
6+   → Full（詳細、複雜）
```

### 三種工作流速查表

```
┌─────────┬──────────┬────────────┬──────────────┐
│ 工作流  │ 時間     │ 文件       │ 適合情況     │
├─────────┼──────────┼────────────┼──────────────┤
│ Lite    │ <30 分鐘 │ 幾乎無     │ 簡單改動     │
│         │          │            │ 樣式、bug    │
├─────────┼──────────┼────────────┼──────────────┤
│ Standard│ 1-2 小時 │ spec + BDD │ 新功能       │
│         │          │            │ 中等複雜度   │
├─────────┼──────────┼────────────┼──────────────┤
│ Full    │ 多天     │ spec + plan│ 系統整合     │
│         │          │ + tasks    │ 金流、複雜   │
└─────────┴──────────┴────────────┴──────────────┘
```

## 🚀 實戰應用

### 給 Agent 的指令範本

#### Lite 工作流範本

```
「把 [描述] 改成 [新的樣子]。
 改完後跑一下測試。」

例子：
「把登入按鈕的背景色從藍色改成綠色。
 改完後檢查懸停時的效果。」
```

#### Standard 工作流範本

```
「我要做 [功能名稱] 功能。

規格：
[完整規格]

請先告訴我：
1. 是否理解了需求？
2. 有沒有疑問？

然後給出：
- 實作計畫（不用寫程式碼）
- 預期的檔案變更

確認沒問題後，我會讓你開始實作。」
```

#### Full 工作流範本

```
「我們要做一個複雜的功能：[功能名稱]

Phase 0: 規格和澄清
[詳細規格]

請列出所有疑問。

Phase 1: 完成澄清後
請做：
1. 研究相關技術和 API
2. 提出詳細實作計畫
3. 識別風險

然後停止。讓我審查計畫。」
```

## 📖 關鍵概念速記

### SDD（規格驅動開發）

```
定義：在寫程式碼前，先把「要做什麼」寫清楚

核心：
  規格 = 目標 + 場景 + 驗收條件

好規格的特徵：
  ✅ 用平白的語言（非技術）
  ✅ 描述「做什麼」，不描述「怎麼做」
  ✅ 包含邊界條件和失敗情況
  ✅ 可驗證（有清晰的驗收標準）

價值：
  消除歧義 → 減少返工 → 節省時間
```

### BDD（行為驅動開發）

```
定義：用「使用者的語言」寫「驗收測試」

格式：Gherkin 語法
  Given [前置條件]
  When [使用者做什麼]
  Then [系統應該怎樣]

三種場景：
  1. 快樂路徑：正常、成功的情況
  2. 錯誤路徑：各種失敗的情況
  3. 邊界路徑：邊界和極端情況

價值：
  既是規格，也是測試
  機器可驗證，人類可讀懂
```

### 複雜度評估

```
用 4 個問題快速判斷難度：
  Q1: 模組數量
  Q2: 權限/並發/不可逆
  Q3: DB Schema 變更
  Q4: 外部 API 整合

分數決定工作流：
  0-2 分  → Lite
  3-5 分  → Standard
  6+ 分   → Full
```

## 🎯 常見問題

### Q1：我應該對所有功能都用 Full 工作流嗎？

**A：不應該。** Full 工作流很詳細，但也很慢。

- 簡單功能用 Lite（5-30 分鐘）
- 中等功能用 Standard（1-2 小時）
- 複雜功能才用 Full（多天）

選擇合適的工作流 = 時間和品質的平衡。

---

### Q2：規格應該寫多詳細？

**A：恰到好處。** 不是越詳細越好。

規格的目的是：
- ✅ 讓 Agent 能理解需求
- ✅ 讓人能驗證實作是否符合
- ❌ 不是替代設計文件

經驗法則：規格通常 1-2 頁就足夠。

---

### Q3：寫 BDD 會不會很耗時？

**A：不會。** BDD 通常比返工修 bug 快得多。

```
無 BDD：寫程式碼 → 品管測試 → 發現問題 → 修 → 再改…
時間：多天

有 BDD：寫 BDD → 寫程式碼 → 自動驗證
時間：少一半，品質好很多
```

---

### Q4：如果需求一直變呢？

**A：流程幫你管理變化。**

```
無流程：
  需求變 → 重新寫程式碼 → 不知道哪裡受影響
  
有流程：
  需求變 → 更新規格 + BDD → 清楚地看到影響
```

流程其實幫你應對變化，不是阻礙。

---

### Q5：Agent 不按照流程呢？

**A：主動管理 Agent。**

- 告訴 Agent 你要用什麼工作流
- 提供明確的規格和計畫
- 要求 Agent 在每一步確認無誤

Agent 就像一個有能力但缺乏方向的工程師。
好的指令 + 清晰的計畫 = 高品質的輸出。
