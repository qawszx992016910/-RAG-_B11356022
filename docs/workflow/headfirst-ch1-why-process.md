# Ch1：為什麼需要流程？

> **本章目標**：理解沒有流程的危害，以及好流程的價值。

---

## 🎬 開場故事：王小明的一週

### 週一上午 10:00

王小明是個中級開發者，他剛剛用上 Claude Code。

PM 給了他一個新需求：

> 「我們需要一個『使用者邀請』功能。
>  Admin 可以透過 email 邀請新使用者加入平台。
>  被邀請者點擊連結設定密碼就能註冊。
>  邀請連結 72 小時內有效。」

王小明想都沒想，直接對 Claude Code 說：

```
「幫我寫使用者邀請功能，spec 就是上面那段。」
```

### 週一下午 13:30

Claude Code 用了 15 分鐘，生成了：
- 新的 database migration
- 3 個新 API 端點
- Email 發送邏輯
- 前端表單元件

共 450 行程式碼。

王小明看了一遍，覺得「還不錯」，就 commit 了。

### 週二上午 09:00

品管開始測試：

```
小明：「這是好的嗎？」

品管：「幾個問題：

1. 我輸入已經註冊的 email，系統回了 200 OK？
2. 一個 email 我可以發無限多個邀請？
3. 為什麼沒有『重新發送邀請』功能？
4. 邀請 token 的生成方式看起來不夠安全…
5. 沒有測試…」

小明：「…我去問 Agent。」
```

### 週二下午 15:00

王小明重新對 Claude Code 說：

```
「已註冊的 email 不能邀請。同一 email 最多 3 個未使用的邀請。
 可以重新發送。Token 用 crypto.randomUUID()。加上測試。」
```

Claude Code 改了一遍程式碼。

但這一次，改出了新的問題：
- 舊的邀請 migration 和新的衝突
- 測試寫得很爛，有 race condition
- Email 模板沒跟著改

又花了 3 小時修。

### 週三

繼續修。

### 週四

終於通過品管審查。

### 結論

**花了 4 天，要做的是 1 天能完成的功能。**

王小明問自己：「我做錯了什麼？」

答案很簡單：**我沒有在開始前問清楚。**

---

## 🔍 剖析：為什麼會發生這種事？

### 問題 1：需求模糊

PM 說的「使用者邀請」，看起來很簡單，但裡面有**很多隱含的假設**：

```
PM 說的：「邀請連結 72 小時內有效」

含義 1：72 小時後，連結自動失效？
含義 2：如果 72 小時內沒有點，能重新發送嗎？
含義 3：重新發送是生成新連結還是延長舊連結？
含義 4：已經點過的連結呢？還能再點嗎？

不同的理解 → 不同的實作 → 不同的問題
```

### 問題 2：缺乏驗收標準

王小明沒有給 Agent 明確的「驗收清單」，所以 Agent 猜測：

```
Agent 猜想 1：同一 email 可以無限邀請
   （因為規格沒有說不行）

Agent 猜想 2：已註冊的使用者也可以再邀請
   （因為規格沒有禁止）

Agent 猜想 3：Token 用簡單的隨機數
   （因為規格沒有說要多安全）

結果：Agent 的「猜測」跟實際需求不符
```

### 問題 3：沒有考慮邊界情況

```
快樂路徑：用戶輸入 email → 發邀請 → 用戶點連結 → 完成註冊
   ✅ 能做

邊界情況呢？
   ❌ 已註冊的 email？
   ❌ 無效的 email？
   ❌ 重複的邀請？
   ❌ 過期的連結？
   ❌ Database 插入失敗？

Agent 沒有考慮 = 程式碼沒有處理 = 測試沒有覆蓋
```

### 問題 4：缺乏明確的測試策略

王小明沒有告訴 Agent：
- ❌ 需要多少測試覆蓋率？
- ❌ 需要單元測試還是整合測試？
- ❌ 邊界情況怎麼測？

Agent 就「隨便寫了一些測試」。

### 問題 5：沒有分階段驗證

王小明一次性丟出所有需求，Agent 一次性寫完所有程式碼。

直到品管測試，才發現問題。

**此時改動成本最高。**

---

## 💡 如果王小明用了流程呢？

### 情景二：有流程的做法

#### 週一上午 10:00

PM 說完需求後，王小明沒有直接寫程式碼，而是：

**第 1 步：寫規格**

```markdown
## 使用者邀請功能規格

### 目標
Admin 可以透過 email 邀請新使用者加入平台

### 使用者場景
1. Admin 打開邀請介面
2. 輸入被邀請者的 email
3. 系統發送邀請信
4. 被邀請者點擊連結
5. 設定密碼完成註冊

### 驗收條件
- [ ] 只有 admin 可以發邀請
- [ ] 已註冊的 email 不能被邀請
- [ ] 同一 email 最多 3 個未使用的邀請
- [ ] 邀請連結 72 小時內有效
- [ ] 可以手動重新發送邀請
- [ ] 邀請 token 使用加密隨機生成
- [ ] 錯誤情況有適當的錯誤訊息

### 邊界情況
- 邀請過期後點連結 → 顯示「邀請已過期」
- 邀請已被使用 → 顯示「此邀請已被使用」
- 非法 token → 顯示「無效的邀請連結」
```

**第 2 步：問澄清問題**

王小明把規格給 PM，並列出疑問：

```
「我有幾個問題：

1. 邀請過期後，能否重新發送給同一個人？
   a) 可以，舊的自動作廢
   b) 可以，但舊的還有效
   c) 不可以，需要 admin 手動審核

2. 『重新發送』是什麼意思？
   a) 發送相同的連結（延長有效期）
   b) 生成新的連結（舊的失效）

3. Non-admin 用戶點邀請連結，能完成註冊嗎？
   還是必須透過 invite-only？

4. Email 不存在或格式錯誤的情況如何處理？
   直接報錯，還是先試著寄信？
」
```

**PM 的回答讓需求變得清晰：**

```
1. 舊的自動作廢（new invites always supersede）
2. 生成新的連結（stateless）
3. 可以，邀請只是加入的一種方式
4. 先驗證格式，格式錯誤直接報錯
```

#### 週一下午 14:00

**第 3 步：制定計畫**

有了清晰的規格和澄清，王小明對 Claude Code 說：

```
「請根據這份規格，給我一個實作計畫。

需要考慮：
1. Database schema（新增什麼表？什麼欄位？）
2. API 設計（需要什麼端點？請求/回應格式？）
3. 測試計畫（什麼需要被測試？）
4. 實作順序（哪些可以並行？哪些有依賴？）

先給我計畫，不用寫程式碼。」
```

Claude Code 生成了詳細的計畫：

```markdown
## 實作計畫

### Phase 1: DB Setup
- 新增 invitations 表
  欄位：id, email, token, status, 
        created_at, expires_at, used_at
- 新增索引以加快查詢

### Phase 2: API 端點設計
POST /api/admin/invitations/send
  請求：{ email: string }
  回應：{ invitationId, expiresAt }
  驗證：admin 角色檢查

POST /api/invitations/:token/accept
  請求：{ password: string }
  回應：{ userId, token (JWT) }

GET /api/admin/invitations
  回應：分頁的邀請列表

POST /api/admin/invitations/:id/resend
  回應：新的邀請資訊

### Phase 3: 具體實作順序
1. Database migration
2. 邀請模型和業務邏輯
3. API 端點
4. 單元測試（邀請邏輯）
5. 整合測試（API）
6. Email 模板
7. 前端表單

### Phase 4: 測試覆蓋
- 單元測試：邀請驗證、過期檢查、token 生成
- 整合測試：API 流程（正常/錯誤）
- E2E 測試（可選）：完整邀請流程
```

王小明和 PM 審查了計畫，確認沒有遺漏。

#### 週一下午 16:00

**第 4 步：逐步實作**

王小明對 Claude Code 說：

```
「按照計畫，先做 Phase 1。
 完成後我們驗證，再做 Phase 2。

Phase 1 的驗收標準：
- Migration 能成功執行
- 表結構符合設計
- 有相應的 index」
```

Claude Code 做完 Phase 1。

王小明驗證：
- ✅ Migration OK
- ✅ 表結構正確
- ✅ Index 建好了

進入 Phase 2。

#### 週二

Phase 2、3、4 逐步完成。

每一步完成後，王小明都要求跑測試。

#### 週三上午

所有 Phase 都完成了。

品管測試：

```
品管：「邀請邏輯全部符合規格。」
小明：「有什麼問題嗎？」
品管：「沒有。通過。」
```

## 🎯 對比：有流程 vs 沒流程

### 無流程

```
需求（模糊）
   ↓
直接寫程式碼
   ↓
品管發現問題
   ↓
返工（成本高）
   ↓
再改…再改…
   ↓
共花 4 天

品質指標：
- 缺陷數：5-10
- 測試覆蓋率：30%
- 返工率：40%
```

### 有流程

```
需求（模糊）
   ↓
寫規格（明確化）
   ↓
澄清問題（消除歧義）
   ↓
制定計畫（預先預防）
   ↓
逐步實作 + 測試（及早發現）
   ↓
共花 2 天

品質指標：
- 缺陷數：0-2
- 測試覆蓋率：85%+
- 返工率：5%
```

---

## 📊 流程的四個價值

### 1. 消除模糊

```
Before:  「邀請系統」 ← 10 種理解
After:   「邀請系統」 ← 1 種共識
```

### 2. 預防而非修復

```
無流程：bug 發現於測試階段 → 改動成本 5 倍
有流程：bug 預防於設計階段 → 成本 1 倍
```

### 3. 加快溝通

```
無流程：「幫我改這個」「還要改什麼？」「…」
有流程：「規格在這裡。你看看缺什麼。」「這三點。」
```

### 4. 提升品質

```
無流程：寫完再測 → 品質取決於 Agent 的「運氣」
有流程：邊寫邊測 → 品質有保證
```

---

## ⚠️ 但流程會不會很繁瑣？

### 常見擔心

> 「流程這麼多步，不會太慢嗎？」

### 實際情況

**不會，反而更快。**

```
無流程：
  寫程式碼：15 分鐘
  測試發現問題：30 分鐘
  返工：3 小時
  ───────────────
  總計：3 小時 45 分鐘

有流程：
  寫規格：10 分鐘
  澄清：10 分鐘
  計畫：10 分鐘
  實作 + 測試：45 分鐘
  ───────────────
  總計：1 小時 15 分鐘
```

**快 3 倍。而且品質更好。**

---

## 🎯 流程的三個層級

根據功能複雜度，你不需要每次都做「完整」流程。

### Lite 流程（簡單功能）

```
需求 → 直接做 → 驗證
(1 句話)        (快速測試)

適合：修改顏色、修改文案、小 bug 修
時間：< 30 分鐘
```

### Standard 流程（中等功能）

```
規格 → 澄清 → 計畫 → 實作 → 驗證
(完整功能)
時間：1-2 小時
```

### Full 流程（複雜功能）

```
規格 → 澄清 → 研究 → 計畫 → 任務 → 實作 → 整合驗證
(複雜系統)
時間：多天
```

之後的章節會詳細講解三種流程。

## 💪 重點整理

### 為什麼需要流程？

```
三句話總結：

1. 沒有流程，模糊的需求會導致錯誤的實作
2. 有流程，問清楚 + 計畫好 = 減少一半的返工
3. 流程不會變慢，反而會變快

核心思想：
「投資 1 小時在規格，省下 3 小時的返工」
```

### 流程的本質

流程不是為了「寫文件」。

流程是為了：
- ✅ 和 Agent 一起**思考清楚**
- ✅ 提前**預防問題**
- ✅ 分階段**驗證**
- ✅ 節省時間和成本

### 你的第一步

別再問 Agent 「幫我做 X」。

開始問：「我想做 X，但我需要先規劃。」

```

2. 你和 PM/Agent 澄清過模糊點嗎？

   □ < 20% ✅
   □ 20-50%
   □ > 50% ⚠️
```

如果你的答案是：
- 「沒有」、「沒有」、「> 50%」

那麼你就是王小明。

你需要這套流程。
