# Ch2：SDD 規格驅動開發

> **本章目標**：學會寫出清晰、完整、可驗證的規格。

---

## 🎯 什麼是規格？

### 規格的定義

```
規格 = 對「要做什麼」的清晰描述

特點：
- ✅ 用平白的語言（不技術性）
- ✅ 描述「做什麼」，不描述「怎麼做」
- ✅ 包含驗收標準（怎麼判斷是對的）
- ✅ 涵蓋邊界情況（邊界怎麼處理）
```

### 規格不是什麼

```
❌ 程式碼
❌ 技術細節（用什麼資料庫、什麼框架）
❌ 實作計畫（步驟應該分開寫）
❌ 長篇幅的文檔（通常 1-2 頁足夠）
```

### 對比：規格 vs 不是規格

#### ❌ 壞規格（模糊）

```
「我們需要使用者登入功能。
 用戶輸入 email 和密碼，
 驗證後回傳 token。」
```

**問題：**
- Token 的格式是什麼？
- 密碼要多複雜？
- 錯誤時回傳什麼？
- 連續失敗怎麼處理？
- 舊 token 還有效嗎？

#### ✅ 好規格（明確）

```
## 使用者登入規格

### 目標
使用者可以透過 email + 密碼登入系統

### 輸入驗證
- Email：必填，格式合法
- 密碼：必填，長度 ≥ 8 字元

### 成功流程
1. 驗證 email 格式
2. 檢查帳號是否存在
3. 比對密碼 hash
4. 生成 JWT token（24 小時有效期）
5. 回傳 200 + token

### 失敗流程
- Email 不存在或密碼錯誤 → 401 "帳號或密碼錯誤"
- 連續失敗 5 次 → 429 "帳號已鎖定，15 分鐘後重試"
- 帳號被停用 → 403 "帳號已被停用"

### 驗收條件
- [ ] 正確的帳密回傳有效 token
- [ ] 錯誤帳密回傳 401
- [ ] 5 次失敗後鎖定 15 分鐘
- [ ] Token 可用於授權其他 API
- [ ] Token 過期後無法使用
```

**區別：**
- 第一個規格 = Agent 猜測空間大 = 結果差異大
- 第二個規格 = 需求明確 = 結果符合預期

## 📋 規格的結構

### 標準規格範本

大多數規格應該包含這些部分：

```
## [功能名稱] 規格

### 1. 目標
用 1-2 句話說明這個功能的目的

### 2. 使用者場景
分步驟描述使用者如何使用這個功能
(步驟 1, 2, 3...)

### 3. 成功流程
系統應該如何回應
(輸入 → 處理 → 輸出)

### 4. 失敗流程
邊界情況和錯誤情況怎麼處理
(各種錯誤的回應)

### 5. 驗收條件
具體的、可驗證的檢查清單
([ ] 能做 X
 [ ] 不能做 Y
 [ ] 當 Z 時...)
```

### 模板實例：使用者頭像上傳

```markdown
## 使用者頭像上傳規格

### 目標
使用者可以上傳或更換個人頭像，系統自動進行裁剪和壓縮

### 使用者場景
1. 使用者點擊「更換頭像」
2. 選擇本地圖片檔案
3. 系統預覽圖片並提供裁剪工具
4. 使用者確認後上傳
5. 系統回傳新頭像的 URL

### 成功流程
- 輸入：JPEG/PNG 圖片，檔案 ≤ 5MB
- 處理：
  1. 驗證檔案類型
  2. 驗證檔案大小
  3. 上傳到 CDN
  4. 生成 3 種尺寸（32x32, 128x128, 256x256）
  5. 更新 DB 中的 avatar_url
- 輸出：200 OK + { avatarUrl: "..." }

### 失敗流程
- 檔案類型不支援 → 400 "僅支援 JPG 和 PNG"
- 檔案過大 → 400 "檔案大小不能超過 5MB"
- 上傳失敗 → 500 "上傳失敗，請重試"

### 驗收條件
- [ ] 支援 JPG 和 PNG
- [ ] 檔案 > 5MB 時拒絕上傳
- [ ] 上傳後生成 3 種尺寸圖片
- [ ] 舊頭像被替換（不保留多個版本）
- [ ] CDN 連結在 24 小時內可用
- [ ] 非登入用戶無法上傳
```

## 🎨 規格的三個層級

根據功能複雜度，規格可以有不同的詳細程度。

### Level 1：簡明式（簡單功能）

適合：修正 bug、小功能、樣式更改

```markdown
## 修改按鈕顏色

### 目標
將登入按鈕的顏色從藍色改成綠色

### 驗收條件
- [ ] 首頁的登入按鈕是綠色
- [ ] 懸停時變成深綠色
- [ ] 手機版也是綠色
```

**特點：簡短，不需要詳細場景和流程**

### Level 2：標準式（中等功能）

適合：新 API、新功能、頁面重構

這個我們上面用過了。包含目標、場景、流程、驗收條件。

### Level 3：詳盡式（複雜功能）

適合：系統整合、資料庫遷移、金流系統

```markdown
## 第三方金流整合（綠界 ECPay）規格

### 1. 目標
用戶可以透過綠界 ECPay 支付訂單，
系統自動確認付款並更新訂單狀態

### 2. 上下文
- 訂單系統已存在
- 已有帳號在綠界開設
- 需要整合綠界 API v2.0

### 3. 使用者場景
詳細步驟（可能 10+ 步）
...

### 4. 成功流程
API 整合細節、回調機制、幂等性...
...

### 5. 失敗流程
網路逾時、重複付款、金額不符...
...

### 6. 邊界條件
退款流程、部分退款、發票、稅務...
...

### 7. 資安考量
金鑰管理、資料加密、PCI 合規...
...

### 8. 驗收條件
15+ 個檢查項目
...
```

**特點：完整，涵蓋所有方面**

## ✍️ 怎麼寫好規格？

### 方法 1：三問法

寫規格時，問自己三個問題：

#### Q1：什麼人會用這個功能？

```
「管理員上傳員工名單」

誰用？→ 管理員
什麼情況？→ 人力資源部招聘後
目的？→ 快速為新員工開帳號
```

#### Q2：這個功能的邊界在哪？

```
支援什麼格式？ → Excel, CSV
最大多少行？ → 1000 行
如果資料重複？ → 跳過該行 + 警告
如果格式錯誤？ → 回滾整個操作
```

#### Q3：怎麼知道它做對了？

```
正常情況：上傳 100 行 → 建立 100 個帳號
重複資料：重複 email 的跳過
失敗情況：格式錯誤時顯示「第 5 行格式錯誤」
```

### 方法 2：場景驅動式

從真實的使用場景開始寫：

```
開始：使用者的具體場景
  ↓
使用者會做什麼（輸入）
  ↓
系統應該回應什麼（輸出）
  ↓
各種邊界情況怎麼處理
  ↓
檢查清單
```

例子：

```
場景：「年底結算，財務需要匯出所有交易記錄」

使用者操作：
1. 登入財務帳號
2. 進入「報表」頁面
3. 選擇「交易明細」
4. 篩選日期 2024/01/01 - 2024/12/31
5. 點擊「匯出 Excel」

系統應該：
1. 驗證用戶是否有財務權限
2. 查詢符合條件的交易（可能數萬筆）
3. 生成 Excel 檔案
4. 傳送下載連結給使用者
5. 保留下載紀錄 (審計)

邊界情況：
- 資料超級多（> 100,000 筆）？ → 分頁下載或分檔
- 匯出失敗？ → 郵件通知，重試連結有效 24 小時
- 有涉密資料？ → 財務才能看，其他人看不到

檢查清單：
- [ ] 權限檢查
- [ ] 支援日期篩選
- [ ] 產生有效 Excel（不是亂碼）
- [ ] 大資料量時表現合理
- [ ] 下載連結有有效期
```

### 方法 3：反問法

問自己一堆「如果...怎麼辦」：

```
如果...使用者沒有填email？
  → 顯示「email 必填」

如果...email 格式不對？
  → 顯示「請輸入有效的 email」

如果...用戶名已存在？
  → 顯示「此用戶名已被使用」

如果...同時有 1000 人註冊？
  → 系統應該能處理（考慮並發）

如果...資料庫掛了？
  → 顯示「系統繁忙，請稍後重試」

如果...使用者點了 10 次提交按鈕？
  → 只建立 1 個帳號（冪等性）
```

## 🎯 規格應該有多詳細？

### 太詳細（過度規範）

```
❌ 「密碼長度必須是 8-16 字元，
     至少一個大寫字母、一個數字、一個特殊字元…」

✅ 「密碼必須符合高強度要求
    (具體標準見 src/validation/password.ts)」
```

**為什麼？** 因為密碼驗證的細節應該在程式碼裡，不是規格裡。

### 太簡略（不足以指導）

```
❌ 「實作使用者登入」

✅ 「使用者可以透過 email + 密碼登入，
    成功時回傳 JWT token，
    失敗時回傳 401 與錯誤訊息」
```

### 平衡點（恰到好處）

```
✅ 規格描述「做什麼」和「驗收條件」
   但不描述「怎麼實作」

✅ 規格說清楚邊界和錯誤情況
   但實作細節留給 Agent

✅ 規格足以讓 Agent 能決策
   但不強制 Agent 只能一種做法
```

## 🔍 常見的規格陷阱

### 陷阱 1：用技術語言寫規格

```
❌ 「實作 OAuth2 flow for social login」

✅ 「使用者可以用 Google/Facebook 帳號直接登入，
    不用另外註冊帳號」
```

**為什麼？** 規格是給人看的，技術細節是實作階段的事。

### 陷阱 2：規格本身有歧義

```
❌ 「使用者可以修改個人資料」
   (修改什麼？可以改什麼？不能改什麼？)

✅ 「使用者可以修改：姓名、大頭貼、簡介、電話
   但不能修改：email、身份證、建帳戶日期」
```

### 陷阱 3：忘記邊界條件

```
❌ 規格只寫快樂路徑（正常情況）

✅ 規格寫：
   - 快樂路徑（成功）
   - 失敗路徑（各種失敗情況）
   - 邊界路徑（邊界條件）
```

### 陷阱 4：規格本身就有矛盾

```
❌ 「郵件必填，但可以不填」
❌ 「只有 admin 可以刪除，同時所有人都能刪除」

快檢查你的規格有沒有自相矛盾的地方
```

### 陷阱 5：需求只來自一個人

```
❌ 你想的規格 ≠ PM 想的規格 ≠ 使用者想的規格

✅ 在寫規格後，讓 PM/使用者審查

問：「這是你們想要的嗎？有遺漏什麼嗎？」
```

## 📝 實戰：寫一個完整規格

### 任務：使用者「封鎖」功能

#### 背景

你的社交 App 中，有使用者反映說某些人的騷擾訊息很煩。

PM 要求：「新增『封鎖使用者』功能」

#### Step 1：理解目標

```
封鎖 = 我看不到那個人的內容，他也看不到我的內容
```

#### Step 2：列出使用者場景

```
1. 使用者在某個人的檔案頁點「封鎖」
2. 系統確認「確定要封鎖此用戶嗎？」
3. 使用者確認
4. 系統建立封鎖關係
5. 被封鎖的人看不到該使用者的貼文和檔案
6. 被封鎖的人無法傳訊息給該使用者
```

#### Step 3：寫成完整規格

```markdown
## 使用者封鎖規格

### 目標
使用者可以封鎖其他使用者，
使被封鎖者無法看到他的內容或聯繫他

### 使用者場景
1. 在某人的檔案頁面，點擊「更多」選單
2. 選擇「封鎖此使用者」
3. 系統顯示確認對話框「要封鎖嗎？此人將看不到你的貼文」
4. 使用者點「是的，封鎖」
5. 頁面返回，該使用者被移出聯絡人列表

### 成功流程
- 輸入：使用者 ID
- 處理：
  1. 驗證封鎖者和被封鎖者不是同一人
  2. 檢查是否已封鎖（防重複）
  3. 建立 blocks 表記錄
  4. 清除共有聊天訊息（只保留系統記錄「已被封鎖」）
- 輸出：200 OK + { status: "blocked" }

### 失敗流程
- 試圖封鎖自己 → 400 "不能封鎖自己"
- 已經封鎖過 → 200 "已經封鎖該使用者"

### 邊界條件
- 被封鎖後，原有的聊天訊息怎麼辦？
  → 該使用者看不到，但訊息仍在 DB（為了舉報等用途）
  
- 被封鎖者能解封嗎？
  → 不能。只有封鎖者可以解封
  
- 被封鎖者能知道自己被封鎖嗎？
  → 不能主動查詢。但如果試著聯繫，看不到對方會猜到

### 驗收條件
- [ ] 使用者可以封鎖其他使用者
- [ ] 使用者可以解除封鎖
- [ ] 被封鎖的人看不到被封鎖者的貼文
- [ ] 被封鎖的人無法傳訊息給被封鎖者
- [ ] 被封鎖的人被移出聯絡人列表
- [ ] 防止重複封鎖同一人
- [ ] 有「已被封鎖」的系統訊息記錄（為了舉報）
```

## 🛠️ 工具：規格檢查清單

寫完規格後，用這個檢查清單驗證：

```
規格檢查清單

□ 目標明確（1-2 句話）
□ 包含使用者場景（分步驟）
□ 包含成功流程（輸入→處理→輸出）
□ 包含失敗流程（至少 3 種失敗情況）
□ 包含邊界條件（at least 3 個「如果...」）
□ 包含驗收條件（at least 5 項，用 checkbox）
□ 沒有技術語言
□ 沒有自相矛盾
□ 沒有假設 Agent 會「猜」
□ 短而清楚（通常 1-2 頁）

如果全部打勾 → 規格及格
如果缺少 3+ 項 → 需要補充
```

## 🎓 總結：SDD 的核心

### SDD（規格驅動開發）的三句話

```
1. 在寫程式碼之前，先寫清楚「要做什麼」

2. 規格應該讓任何人（包括 Agent）都能理解

3. 規格消除模糊 = 減少返工 = 節省時間
```

### 規格的三要素

```
目標 + 場景 + 驗收條件 = 好規格
```

### 寫規格的三個方法

```
1. 三問法：問「誰用」「邊界是什麼」「怎麼知道對了」
2. 場景驅動：從真實使用場景開始
3. 反問法：問自己「如果...怎麼辦」
```
