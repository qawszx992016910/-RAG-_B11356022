# Ch4：複雜度評估與工作流選擇

> **本章目標**：學會用四問題法快速評估功能複雜度，選擇合適的工作流。

---

## 🎯 核心問題

你已經學了 SDD、BDD、還有各種流程。

但問題是：**我應該對每個功能都套用完整流程嗎？**

答案：**不應該。**

```
修改按鈕顏色 → 簡單，用 Lite 工作流（5 分鐘）
新增 API 端點 → 中等，用 Standard 工作流（1 小時）
整合金流系統 → 複雜，用 Full 工作流（多天）

同一套流程用在三種情況 = 要麼浪費時間，要麼品質不夠
```

所以，我們需要一個方法來：

1. **快速判斷**功能的複雜度
2. **選擇合適的**工作流深度
3. **分配足夠的**時間和資源

這就是「複雜度評估」。

---

## 📊 四問題複雜度評估法

### 方法介紹

回答以下 4 個問題，每個有不同的分數：

```
Q1: 涉及多少模組或服務？
Q2: 有權限、並發或不可逆操作嗎？
Q3: 涉及 DB Schema 變更嗎？
Q4: 涉及外部 API 整合嗎？

總分決定工作流級別
```

### 問題詳解

#### Q1：涉及多少模組或服務？

**定義**：「模組」= 程式碼的獨立部分或獨立服務

```
得分 0 分：只涉及 1 個模組
  例：修改 UI 元件的樣式
     修改一個工具函式
     前端表單驗證

得分 2 分：涉及 2 個或以上模組
  例：前端表單 + 後端 API
     User 模組 + Auth 模組
     Database + Cache
```

**評估技巧**：
```
畫一個「模組圖」，看會涉及多少個方塊：

1 個方塊？ → 0 分
┌───────┐
│ Button│
└───────┘

2+ 個方塊？ → 2 分
┌───────┐   ┌────────┐
│前端表單│ → │後端API  │
└───────┘   └────────┘
     ↓
┌──────────┐
│ Database │
└──────────┘
```

---

#### Q2：有權限、並發或不可逆操作嗎？

**定義**：
- **權限**：只有某些人能做
- **並發**：多人同時操作
- **不可逆**：刪除、轉帳等無法撤銷的操作

```
得分 0 分：都沒有
  例：修改按鈕顏色（誰都能改）
     寫個前端工具函式（沒有並發問題）
     增加一個日誌欄位（可以撤銷）

得分 3 分：有至少一個
  例：只有 Admin 能刪除使用者（權限）
     多個使用者同時修改訂單（並發）
     轉帳操作（不可逆）
     封鎖使用者（不可逆 + 權限）
```

**評估技巧**：
```
問自己：
□ 這個操作只有某些人能做嗎？
□ 多個人同時操作會出問題嗎？
□ 這個操作能刪除資料或轉移金錢嗎？

如果有任何一個「是」 → 3 分
全部「否」 → 0 分
```

---

#### Q3：涉及 DB Schema 變更嗎？

**定義**：新增/修改資料庫表、欄位、索引、約束

```
得分 0 分：不涉及 DB 變更
  例：API 查詢現有資料
     修改前端

得分 2 分：涉及 DB 變更
  例：新增 users 表
     給 orders 表加 status 欄位
     新增索引以加快查詢
     修改約束條件
```

**評估技巧**：
```
問自己：
□ 需要新建表嗎？
□ 需要修改現有的表結構嗎？
□ 需要新增或修改索引嗎？
□ 需要寫 migration 檔案嗎？

有任何一個「是」 → 2 分
全部「否」 → 0 分
```

---

#### Q4：涉及外部 API 整合嗎？

**定義**：呼叫系統外部的 API（第三方服務）

```
得分 0 分：不涉及外部 API
  例：純前端功能
     系統內部 API

得分 2 分：涉及外部 API
  例：呼叫 Google OAuth
     整合金流 API（綠界、Line Pay）
     傳送 SMS（Twilio）
     發送信件（SendGrid）
     翻譯服務（Google Translate）
```

**評估技巧**：
```
問自己：
□ 需要呼叫第三方服務嗎？
□ 需要處理 API key 和認證嗎？
□ 需要處理 API 的失敗和重試嗎？

有任何一個「是」 → 2 分
全部「否」 → 0 分
```

## 📈 計分與工作流對應

### 評估表格

```
┌─────┬────┬────┬────┬────┬──────────────┐
│ Q1  │ Q2 │ Q3 │ Q4 │總分 │ 工作流       │
├─────┼────┼────┼────┼────┼──────────────┤
│  0  │ 0  │ 0  │ 0  │ 0  │ Lite         │
│  0  │ 0  │ 0  │ 2  │ 2  │ Lite         │
│  0  │ 0  │ 2  │ 0  │ 2  │ Lite         │
│  2  │ 0  │ 0  │ 0  │ 2  │ Lite → Std   │
├─────┼────┼────┼────┼────┼──────────────┤
│  2  │ 0  │ 2  │ 0  │ 4  │ Standard     │
│  2  │ 3  │ 0  │ 0  │ 5  │ Standard     │
│  0  │ 3  │ 2  │ 0  │ 5  │ Standard     │
├─────┼────┼────┼────┼────┼──────────────┤
│  2  │ 3  │ 2  │ 0  │ 7  │ Full         │
│  2  │ 3  │ 2  │ 2  │ 9  │ Full         │
│  2  │ 3  │ 0  │ 2  │ 7  │ Full         │
└─────┴────┴────┴────┴────┴──────────────┘
```

### 分數區間

```
0-2 分  → Lite 工作流 (~30 分鐘)
3-5 分  → Standard 工作流 (~1-2 小時)
6+ 分   → Full 工作流 (~多天)
```

## 🎯 三種工作流詳解

### Lite 工作流（0-2 分）

適合：簡單的前端修改、bug 修復、小工具

#### 流程圖

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│ 需求描述  │ → │ 直接實作  │ → │ 驗證測試  │
│(1 句話)  │   │(不需計畫) │   │(快速檢查) │
└──────────┘   └──────────┘   └──────────┘

時間：< 30 分鐘
文件：幾乎沒有
```

#### 工作內容

```
Step 1：簡短的需求描述（可以就 1-2 句話）
Step 2：Agent 直接寫程式碼（不需要計畫、規格）
Step 3：快速驗證（跑測試或手動測）
Step 4：完成
```

#### 例子

```
需求：「把登入按鈕的顏色從藍色改成綠色」

→ Agent 直接修改 CSS
→ 檢查按鈕顏色是否正確
→ 完成（5 分鐘）
```

#### 給 Agent 的指令風格

```
簡短、直接、不需要背景：

「把首頁的『開始』按鈕改成綠色，
 懸停時變深綠。」

「修正 DateFormatUtil 中的時區 bug。」

「把表單的錯誤訊息字體從紅色改成橙色。」
```

---

### Standard 工作流（3-5 分）

適合：新功能、元件升級、中等複雜度的改動

#### 流程圖

```
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│ 規格   │ → │ 澄清   │ → │ 計畫   │ → │ 實作   │ → │ 驗證   │
│(文件) │   │(問題) │   │(分解) │   │(代碼) │   │(測試) │
└────────┘   └────────┘   └────────┘   └────────┘   └────────┘

時間：1-2 小時
文件：spec.md + BDD scenarios
```

#### 工作內容

```
Step 1：寫規格（目標、場景、驗收條件）
Step 2：澄清（問 Agent 5 個關鍵問題）
Step 3：制定計畫（任務分解、順序）
Step 4：實作（按計畫寫程式碼）
Step 5：驗證（測試覆蓋、BDD 情境通過）
```

#### 例子

```
功能：「使用者可以修改個人檔案」

Step 1：寫規格
  目標、可修改的欄位、驗收條件

Step 2：澄清
  Q: 非登入使用者可以修改嗎？
  Q: 修改 email 需要重新驗證嗎？
  Q: 修改密碼需要輸入舊密碼嗎？
  ...

Step 3：計畫
  1. 前端表單（修改欄位）
  2. 後端 API（POST /api/profile）
  3. 驗證邏輯
  4. 測試

Step 4：實作
  Agent 寫程式碼

Step 5：驗證
  所有測試通過 + BDD 情境完成
```

#### 給 Agent 的指令風格

```
結構化、有背景、清楚預期：

「這是『使用者修改檔案』功能的規格：
 [規格內容]

 請先審視規格，如有疑問列出來。
 然後給出實作計畫（不用寫程式碼）。」

然後：

「根據計畫，逐步實作：
 1. 建立 API 端點
 2. 寫驗證邏輯
 3. 新增測試
 
 每步完成後跑測試。」
```

### Full 工作流（6+ 分）

適合：複雜系統、資料庫遷移、金流系統、第三方整合

#### 流程圖

```
Phase 0: 規格 + 澄清
  ↓
Phase 1: 研究 + 計畫
  ↓
🛑 人類審查點（確認計畫無誤）
  ↓
Phase 2: 任務分解
  ↓
Phase 3: 逐步實作
  ↓
Phase 4: 整合驗證
  ↓
🛑 測試驗收

時間：多天（2-5 天）
文件：spec.md + 研究筆記 + plan.md + tasks.md
```

#### 工作內容

```
Phase 0：規格與澄清
  - 寫詳細規格（3-5 頁）
  - 列出所有疑問
  - 確保 Agent 完全理解

Phase 1：研究與計畫
  - Agent 研究相關 API、技術
  - 提出詳細的實作計畫
  - 識別風險和挑戰
  
🛑 人類審查（你要認真看）
  - 確認計畫是否合理
  - 是否有遺漏
  - 風險評估

Phase 2：任務分解
  - Agent 將計畫分解成 10+ 個小任務
  - 標記任務間的依賴
  - 估計每個任務的時間

Phase 3：逐步實作
  - Agent 按任務順序實作
  - 每個任務完成後驗證
  - 如果出現問題，及時調整

Phase 4：整合驗證
  - 所有任務集成
  - 跑完整的測試套件
  - E2E 測試（如適用）
```

#### 例子

```
功能：「整合第三方金流（綠界 ECPay）」

評估：
  Q1: 金流服務 + 訂單系統 = 2 分
  Q2: 有權限（admin 設置）+ 不可逆（轉帳）= 3 分
  Q3: 可能需要 transactions 表 = 2 分
  Q4: 呼叫綠界 API = 2 分
  ─────────────────────────────
  總分：9 分 → Full 工作流

Phase 0：規格澄清
  [詳細規格：流程、安全、幂等性、退款等]
  
  澄清點：
  - 是否支援部分退款？
  - 如何處理重複請求？
  - 發票如何整合？

Phase 1：研究
  Agent 研究綠界 API：
  - 身份驗證方式
  - 各個端點的功能
  - 錯誤處理方式
  - 重試策略
  
  提出計畫：
  - 後端整合點
  - 資料庫設計
  - 安全考慮
  - 測試策略

🛑 你審查計畫
  - 是否覆蓋所有場景？
  - 安全性是否足夠？
  - 有沒有遺漏？

Phase 2：任務分解
  1. DB migration（新增 transactions 表）
  2. 綠界 API client（基本集成）
  3. 支付初始化 API
  4. 支付回調處理
  5. 退款 API
  6. 訂單狀態更新邏輯
  7. 錯誤處理和日誌
  8. 單元測試
  9. 整合測試
  10. E2E 測試
  11. 文件和部署指南

Phase 3：實作
  Task 1 → 測試通過 → Task 2 → 測試通過 → ...

Phase 4：整合驗證
  - 所有單元測試通過
  - 所有整合測試通過
  - 手動 E2E 測試（完整流程）
  - 沙箱環境驗證
```

#### 給 Agent 的指令風格

```
詳細、分階段、有明確檢查點：

「我們要整合綠界 ECPay 支付。

Phase 0：
  [完整規格，包括所有邊界情況]
  
  請列出你的疑問。

Phase 1：
  [收到澄清後]
  請研究綠界文件並提出詳細計畫。
  包括：
  - DB 設計
  - API 端點設計
  - 錯誤處理策略
  - 安全考慮
  - 風險評估

Phase 2：
  [我審查計畫後]
  將計畫分解成具體任務。
  包括依賴和順序。

Phase 3：
  按任務逐步實作。
  每個任務：
  1. 寫程式碼
  2. 寫測試
  3. 測試通過
  4. 報告進度

Phase 4：
  整合所有任務。
  跑完整測試套件。」
```

## 🔄 流程升級

有時，初始評估是 Standard，但做著做著發現應該用 Full。

### 何時升級？

```
跡象 1：發現需要 API 整合
  「等等，邀請功能需要整合 Email API 嗎？」
  Standard → Full

跡象 2：並發問題出現
  「多個使用者同時操作，資料不一致…」
  Lite → Standard
  Standard → Full

跡象 3：涉及金錢或敏感資料
  「這個功能涉及轉帳…」
  任何級別 → Full

跡象 4：Agent 說「我需要更多資訊」
  「規格還不夠清楚，我無法決策…」
  當前級別 → 上一級別
```

### 升級方法

```
不用重新開始，只需：

1. 停止當前工作
2. 補充缺少的規格
3. 做額外的澄清
4. 重新評估複雜度
5. 決定是否升級
6. 如果升級，執行额外的流程
```

## 🎯 實戰案例

### 案例 1：修改表單輸入框寬度

```
功能：把「用戶名」輸入框的寬度從 200px 改成 300px

評估：
  Q1: 只改一個元件（前端） = 0 分
  Q2: 沒有權限、並發、不可逆問題 = 0 分
  Q3: 不涉及 DB = 0 分
  Q4: 不涉及外部 API = 0 分
  ─────────────────────────────
  總分：0 分 → Lite 工作流

執行：
  時間：5 分鐘
  流程：「改一下寬度」→ Agent 改 → 檢查 → 完成
```

---

### 案例 2：OAuth 第三方登入

```
功能：使用者可以用 Google 帳號直接登入，不用另外註冊

評估：
  Q1: 前端（按鈕 + callback）+ 後端（API）= 2 分
  Q2: 涉及認證（權限控制）= 3 分
  Q3: 不涉及 DB Schema 變更（users 表已有 provider 欄位）= 0 分
  Q4: 呼叫 Google OAuth API = 2 分
  ─────────────────────────────
  總分：7 分 → Full 工作流？

  等等，重新評估 Q3：
  - 不需要新表，users 表已有 google_id 欄位
  = 0 分

  重新評估 Q2：
  - 雖然涉及認證，但 OAuth 是標準流程，沒有複雜的並發或不可逆操作
  - 降級為較輕量的權限控制
  = 3 分

  實際上：
  Q1: 2 分 + Q2: 3 分 + Q3: 0 分 + Q4: 2 分 = 7 分
  → 但外部 API 是成熟的標準協議（OAuth 2.0）
  → 風險可控，不需要 Full 流程中的多日研究和任務分解

  決定：用 Standard 工作流（偏上限）
  原因：
  - Google OAuth 有成熟的 SDK 和文件
  - 流程相對固定，不需要大量研究
  - 但仍需規格（帳號衝突怎麼辦？）和計畫

執行：
  時間：1-2 小時
  流程：規格 → 澄清 → 計畫 → 實作 → 驗證
```

> 💡 **學習點**：分數是指南，不是絕對標準。
> 如果外部 API 是成熟標準（OAuth、Stripe），
> 可以適度降級工作流。
> 反之，如果 API 不穩定或文件不全，應該升級。

### 案例 3：新增用戶註冊功能

```
功能：新的 API 端點讓使用者自己註冊（之前只能 admin 邀請）

評估：
  Q1: 前端（表單）+ 後端（API）+ DB = 2 分
  Q2: 有 email 驗證（多步）但無權限問題 = 0 分
  Q3: 可能需要 email_verification 表 = 2 分
  Q4: 需要 Email API（如 SendGrid）= 2 分
  ─────────────────────────────
  總分：6 分 → Full 工作流？
  
  等等，重新評估 Q2：
  - 新使用者可以自己決定是否驗證（沒有權限控制）
  - 不涉及轉帳等不可逆操作
  = 0 分

  實際上：
  Q1: 2 分 + Q2: 0 分 + Q3: 2 分 + Q4: 2 分 = 6 分
  → 邊界的 Full（或升級的 Standard）
  
  決定：用 Full 工作流（因為涉及 Email 整合）

執行：
  時間：2-5 天
  流程：規格 → 澄清 → 研究 → 計畫 → 審查 →
        任務分解 → 逐步實作 → 整合驗證
```

### 案例 4：整合 Apple Pay 支付

```
功能：用戶可以用 Apple Pay 支付訂單

評估：
  Q1: App（前端）+ 後端（API）+ 金流服務 = 2 分
  Q2: 涉及金錢（不可逆） = 3 分
  Q3: 需要 payments 表或修改 orders 表 = 2 分
  Q4: 呼叫 Apple 支付 API + 銀行 API = 2 分
  ─────────────────────────────
  總分：9 分 → Full 工作流

執行：
  時間：3-5 天
  流程：規格 → 澄清 → 研究 → 計畫 → 審查 → 
        任務分解 → 逐步實作 → 整合驗證 → 沙箱測試
```

## ⚠️ 評估陷阱

### 陷阱 1：高估複雜度

```
❌ 「使用者改頭像，涉及文件上傳，用 Full 工作流」

✅ 正確評估
  Q1: 前端 + 後端 = 2 分
  Q2: 沒有特殊權限、並發或不可逆 = 0 分
  Q3: 不改 DB schema（只改 avatar_url）= 0 分
  Q4: 可能用 CDN 但通常是配置，不是新整合 = 0 分
  → 2 分 = Lite / Standard 工作流
```

### 陷阱 2：低估複雜度

```
❌ 「訂單系統，Lite 工作流 30 分鐘完成」

✅ 正確評估
  Q1: 訂單 + 用戶 + 支付 + 庫存 = 2 分
  Q2: Admin 才能創建訂單 + 不可逆 = 3 分
  Q3: 新增 orders, order_items 表 = 2 分
  Q4: 呼叫支付 API = 2 分
  → 9 分 = Full 工作流（多天）
```

### 陷阱 3：忽略新手 Agent

```
問題：Agent 第一次接觸某個技術

例：「整合 OAuth」
  如果 Agent 沒用過 OAuth → 額外研究時間
  評估可能需要升級一級

解決：告訴 Agent「這是你第一次接觸 X 嗎？」
     讓 Agent 評估是否需要額外時間
```

## 🎓 總結

### 四問題法速記

```
Q1: 模組數？ (1=0, 2+=2)
Q2: 權限/並發/不可逆？ (否=0, 是=3)
Q3: DB 改動？ (否=0, 是=2)
Q4: 外部 API？ (否=0, 是=2)

0-2 → Lite (快)
3-5 → Standard (中)
6+  → Full (慢)
```

### 三種工作流對比

```
           Lite      Standard    Full
─────────────────────────────────────
時間       < 30分    1-2 小時    多天
文件       幾乎無    spec+BDD   spec+計畫+任務
流程       直接做    spec→計畫→做 多階段+審查
適合範圍   簡單      中等        複雜
成功率     80%       95%        99%
```

### 何時升級流程？

```
徵兆：
  - Agent 說需要更多資訊
  - 發現了新的複雜性
  - 涉及金錢或敏感資料
  - 多個人同時操作
  
行動：升級到更詳細的工作流
```
