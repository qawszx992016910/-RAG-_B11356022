# Ch5：Lite 工作流實戰

> **本章目標**：看一個完整的 Lite 工作流案例，從需求到完成只需 30 分鐘。

---

## 🎬 Lite 工作流概覽

```
特徵：
  ✅ 簡單、快速
  ✅ 沒有複雜的規格或計畫
  ✅ 直接寫 → 直接驗證
  ✅ 適合 0-2 分的功能

流程：
  需求描述（1 句話）
    ↓
  直接實作（Agent 寫程式碼）
    ↓
  驗證測試（快速檢查）
    ↓
  完成

時間：5-30 分鐘
文件：幾乎沒有
成功率：80%
```

## 案例 1：修改按鈕顏色

### 背景

你的應用首頁有一個藍色的「開始」按鈕。

設計師說：「把它改成綠色，懸停時要深綠。」

### 複雜度評估

```
Q1: 只改 UI 元件（前端） = 0 分
Q2: 沒有權限、並發問題 = 0 分
Q3: 不涉及 DB = 0 分
Q4: 不涉及外部 API = 0 分
─────────────────────
總分：0 分 → Lite 工作流 ✅
```

### 執行流程

#### Step 1：給 Agent 清晰的需求（1 分鐘）

```
「把首頁的『開始』按鈕改成綠色。
 正常狀態是綠色（#22c55e），
 懸停時是深綠色（#16a34a）。

 完成後檢查一下頁面效果。」
```

**重點：**
- ✅ 明確指出要改什麼（「開始」按鈕）
- ✅ 明確指出改成什麼（綠色 + 顏色值）
- ✅ 明確指出檢查方式（看看效果）

#### Step 2：Agent 實作（3 分鐘）

Agent 回應：

```
好的，我來修改首頁按鈕的顏色。

檢查中...
找到了 src/components/HomePage.tsx 中的 StartButton

當前代碼：
<button className="bg-blue-600 hover:bg-blue-700">
  開始
</button>

改成：
<button className="bg-green-500 hover:bg-green-700">
  開始
</button>

或用 inline style：
<button style={{
  backgroundColor: '#22c55e',
  ...
}}
onMouseOver={...}
>
  開始
</button>

要我用哪種方式？我建議用 Tailwind CSS 的 green-500 和 green-700，
更容易維護。
```

#### Step 3：你確認（1 分鐘）

```
「用 Tailwind CSS。改好了嗎？」
```

Agent：

```
完成了。改動：

src/components/HomePage.tsx:
- className="bg-blue-600 hover:bg-blue-700"
+ className="bg-green-500 hover:bg-green-700"

測試建議：
1. 開啟首頁
2. 看按鈕是否是綠色
3. 懸停看是否變深綠
```

#### Step 4：驗證（2 分鐘）

你開啟應用：

```
✅ 按鈕是綠色的
✅ 懸停時變深綠
✅ 文字清晰可見

完美！
```

### 完成

**總時間：5 分鐘**

```
需求描述（1 min）→ 實作（3 min）→ 驗證（1 min）

完成 ✅
```

## 案例 2：修正時間格式 Bug

### 背景

用戶報告說：「訂單列表中的日期顯示錯誤。應該顯示 '2024-04-08'，但顯示成 '2024/04/08'。」

### 複雜度評估

```
Q1: 只涉及 UI（前端顯示） = 0 分
Q2: 沒有特殊問題 = 0 分
Q3: 不涉及 DB = 0 分
Q4: 不涉及外部 API = 0 分
─────────────────────
總分：0 分 → Lite 工作流 ✅
```

### 執行流程

#### Step 1：給 Agent 清晰的需求（1 分鐘）

```
「訂單列表中的日期顯示格式錯誤。

當前：2024/04/08
應該：2024-04-08

檔案位置：src/components/OrderList.tsx
函式名稱：formatOrderDate（或類似的）

改好後測試一下列表是否正確顯示。」
```

**重點：**
- ✅ 明確說出問題（格式錯誤）
- ✅ 明確說出當前和目標（/ 改成 -）
- ✅ 指出檔案位置（幫 Agent 快速找到）

#### Step 2：Agent 實作（2 分鐘）

Agent 回應：

```
找到了問題。

src/utils/dateFormat.ts:

當前代碼：
export const formatOrderDate = (date: Date) => {
  return date.toLocaleDateString('en-US'); // 結果是 YYYY/MM/DD
}

改成：
export const formatOrderDate = (date: Date) => {
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');
  return `${year}-${month}-${day}`;
}

或用 date-fns：
import { format } from 'date-fns';
export const formatOrderDate = (date: Date) => {
  return format(date, 'yyyy-MM-dd');
}

你已經用 date-fns 嗎？
```

#### Step 3：你確認（1 分鐘）

```
「用 date-fns，因為我們已經在用。改好了嗎？」
```

Agent：

```
完成了。改動：

src/utils/dateFormat.ts:
import { format } from 'date-fns';

export const formatOrderDate = (date: Date) => {
  return format(date, 'yyyy-MM-dd');
}

現在訂單列表應該顯示 YYYY-MM-DD 格式。

如果有其他地方也用到這個函式，會一起修正。
```

#### Step 4：驗證（2 分鐘）

你開啟訂單列表：

```
✅ 日期現在是 2024-04-08 格式
✅ 所有訂單列表都正確
✅ 沒有破壞其他功能

完美！
```

### 完成

**總時間：5 分鐘**

## 案例 3：新增表單欄位

### 背景

PM 說：「使用者反饋，希望在『聯繫我們』表單上加一個『公司名稱』欄位。」

### 複雜度評估

```
Q1: 只涉及表單（前端） = 0 分
Q2: 沒有特殊問題 = 0 分
Q3: 不涉及 DB（先不考慮存儲） = 0 分
Q4: 不涉及外部 API = 0 分
─────────────────────
總分：0 分 → Lite 工作流 ✅

（注：如果要存儲到 DB，會升級為 Standard）
```

### 執行流程

#### Step 1：給 Agent 清晰的需求（2 分鐘）

```
「在『聯繫我們』表單中新增『公司名稱』欄位。

要求：
- 欄位名稱：Company Name（companyName）
- 位置：在『Email』欄位下方
- 是否必填：否（可選）
- 驗證：無特殊驗證

檔案位置：src/components/ContactForm.tsx

改好後測試一下表單是否能正常渲染。」
```

#### Step 2：Agent 實作（3 分鐘）

Agent 回應：

```
找到了表單。

src/components/ContactForm.tsx

當前欄位：
- Name（name）
- Email（email）
- Message（message）

我會加入：
- Company Name（companyName）
  位置：Email 下方

更新：
1. 表單 state 加入 companyName
2. 新增 input 欄位
3. 更新 handleChange 處理邏輯
4. 表單提交時包含 companyName

做好了。預覽一下：

<input 
  type="text"
  placeholder="Company Name"
  value={formData.companyName}
  onChange={(e) => setFormData({...formData, companyName: e.target.value})}
/>
```

#### Step 3：驗證（2 分鐘）

你開啟表單：

```
✅ 新欄位『Company Name』顯示在 Email 下方
✅ 可以輸入文字
✅ 表單提交時能抓到資料
✅ 其他欄位沒有受影響

完美！
```

### 完成

**總時間：10 分鐘**

## Lite 工作流的常見場景

```
修改樣式 / 顏色 / 尺寸
  「把這個按鈕改成…」
  時間：5-10 分鐘

修正文案 / 標籤
  「把『確定』改成『同意』」
  時間：2-5 分鐘

修復簡單 Bug
  「日期格式不對」
  時間：5-15 分鐘

新增簡單欄位
  「表單加一個新欄位」
  時間：10-20 分鐘

移除不用的功能
  「刪掉側邊欄的『通知』按鈕」
  時間：5-10 分鐘

更新常量或配置
  「把 API URL 改成…」
  時間：2-5 分鐘
```

## Lite 工作流的最佳實踐

### ✅ 做這些事

```
1. 清楚指出「改什麼」
   ✅ 「把首頁的『開始』按鈕改成綠色」
   ❌ 「改一下顏色」

2. 如果可能，給出具體位置
   ✅ 「src/components/Button.tsx 中的 StartButton」
   ❌ 「某個地方的某個按鈕」

3. 給出具體數值或標準
   ✅ 「綠色（#22c55e）」
   ✅ 「YYYY-MM-DD 格式」
   ❌ 「看起來應該改一下」

4. 驗證後再 commit
   ✅ 檢查效果，確認無誤後再提交
   ❌ 直接接受 Agent 的輸出

5. 問題明確時，保持指令簡短
   ✅ 一句話或兩句話
   ❌ 長篇幅解釋
```

### ❌ 避免這些事

```
1. 模糊的需求
   ❌ 「改一下這裡」
   ❌ 「看起來不對」

2. 多個需求混在一起
   ❌ 「改按鈕顏色、加新欄位、修復 bug、更新文案」
   → 分開，每個用一次 Lite 工作流

3. 期望 Agent 猜你的意思
   ❌ 「改一下表單」（改什麼？怎麼改？）

4. 沒有驗證就認為完成
   ❌ Agent 說「done」，你就提交了
   → 親自檢查，確保符合預期

5. 對簡單改動也寫超詳細的規格
   ❌ 改個顏色卻寫 5 頁規格
   → 簡單改動，簡短指令
```

## Lite 工作流的陷阱

### 陷阱 1：需求其實沒那麼簡單

```
你認為：「修改表單欄位，Lite 工作流」
Agent 做了後，發現：
  - 欄位需要存儲到 DB（多了 migration）
  - 需要後端 API 支持（多了端點）
  - 需要驗證邏輯（多了檢查）
  
結果：不是 Lite，應該是 Standard

解決：先評估複雜度。如果涉及 DB，升級為 Standard。
```

### 陷阱 2：改動影響其他地方

```
你改了日期格式函式。
結果：
  - 報表頁面的日期也變了（可能不想要）
  - API 回應格式改了（可能破壞前端其他部分）

解決：改動前，搜索一下這個函式在哪裡被使用。
      告訴 Agent：「只改首頁的日期顯示，不要影響其他地方」
```

### 陷阱 3：樣式改動沒有響應式設計

```
你改了按鈕寬度為 300px。
結果：
  - 桌面上看起來不錯
  - 手機上按鈕被切掉了

解決：檢查改動後在不同設備上的效果。
      告訴 Agent：「確保在手機和平板上也正常顯示」
```

### 陷阱 4：Lite 工作流適用範圍

```
❌ 不應該用 Lite：
  - 需要新增 API 端點
  - 需要修改資料庫
  - 涉及多個模組的協調
  - 涉及權限或並發

✅ 應該用 Lite：
  - 純前端改動
  - 單一檔案的改動
  - 不影響其他功能
  - 15 分鐘內能完成並驗證
```

## 🧠 快速參考：Lite 工作流指令範本

### 修改樣式

```
「把 [元件名稱] 的 [屬性] 改成 [新值]。
 確認 [設備/頁面] 上效果正常。」

例子：
「把首頁的『開始』按鈕改成綠色（#22c55e），
 懸停變深綠（#16a34a）。確認手機和桌面都正常。」
```

### 修正 Bug

```
「[問題描述]。
 應該 [期望表現]。
 檔案：[位置]。」

例子：
「日期格式顯示錯誤。
 應該是 YYYY-MM-DD，現在是 YYYY/MM/DD。
 檔案：src/utils/dateFormat.ts」
```

### 新增簡單欄位

```
「在 [表單/頁面] 的 [位置] 新增欄位：
 欄位名：[名稱]
 類型：[text/email/number/etc]
 必填：[是/否]」

例子：
「在『聯繫我們』表單的『Email』下方新增欄位：
 欄位名：Company Name
 類型：text
 必填：否」
```

### 更新文案

```
「把 [地點] 的『[舊文案]』改成『[新文案]』」

例子：
「把首頁按鈕的『開始使用』改成『立即開始』」
```

```
□ 15 分鐘內完成了嗎？

□ 沒有破壞其他功能嗎？

```

## 💡 何時升級到 Standard？

如果你發現以下任何一個，立即升級到 Standard 工作流：

```
❌ 涉及後端 API 修改
❌ 涉及資料庫改動
❌ 影響多個相關功能
❌ 需要寫新的測試（不只是手動驗證）
❌ 不確定會不會破壞什麼
❌ 有權限或並發考慮

→ 停止 Lite，使用 Standard 工作流
```
