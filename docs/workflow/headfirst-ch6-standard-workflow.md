# Ch6：Standard 工作流實戰

> **本章目標**：看一個完整的 Standard 工作流案例，從規格到完成需要 1-2 小時。

---

## 🎬 Standard 工作流概覽

```
特徵：
  ✅ 中等複雜度（3-5 分）
  ✅ 需要規格和計畫
  ✅ 涉及前端 + 後端，或後端改動
  ✅ 需要規格、澄清、計畫的完整流程

流程：
  規格撰寫
    ↓
  澄清問題
    ↓
  計畫實作
    ↓
  逐步實作 + 測試
    ↓
  完成驗證

時間：1-2 小時
文件：spec.md + BDD scenarios
成功率：95%
```

## 案例：使用者個人檔案修改功能

### 背景故事

你的應用中，使用者可以查看個人檔案，但無法修改。

PM 說：「新增『編輯檔案』功能，讓使用者可以修改自己的姓名、頭像、簡介。」

### 複雜度評估

```
Q1: 涉及前端（表單）+ 後端（API）+ DB = 2 分
Q2: 只有登入使用者可以修改自己的資料（權限控制）
    + 頭像上傳覆蓋舊檔（不可逆）= 3 分
Q3: 不涉及 DB Schema 變更（欄位已存在）= 0 分
Q4: 不涉及外部 API = 0 分
──────────────────────────────────────
總分：5 分 → Standard 工作流 ✅

決定：用 Standard 工作流
原因：
  - Q2 分數較高（認證 + 覆蓋舊頭像不可逆）
  - 需要清晰的規格（什麼可以改，什麼不能改）
  - 涉及後端和前端的協調
  - 需要測試計畫
```

## Phase 1：規格撰寫（15 分鐘）

### Step 1：寫規格

```markdown
## 使用者檔案編輯規格

### 目標
使用者可以編輯自己的個人檔案信息，
包括姓名、頭像、簡介

### 使用者場景
1. 使用者進入個人檔案頁面
2. 點擊「編輯」按鈕進入編輯模式
3. 修改姓名、頭像、簡介
4. 點擊「保存」提交變更
5. 頁面回到查看模式，顯示更新後的資訊

### 可編輯的欄位
- 姓名（displayName）
  - 必填
  - 長度 1-50 字元
  
- 頭像（avatar）
  - 可選
  - 支援上傳新圖片或移除
  - 檔案大小 ≤ 5MB，格式 JPG/PNG
  
- 簡介（bio）
  - 可選
  - 長度 0-500 字元

### 不可編輯的欄位
- Email（已驗證，不能改）
- 用戶名（系統生成，不能改）
- 建帳戶日期（系統資訊）

### 成功流程
1. 使用者點「編輯」→ 進入編輯模式
2. 填寫表單 → 驗證成功
3. 點「保存」→ 發送 PATCH /api/profile
4. 後端驗證 + 儲存到 DB
5. 回傳 200 + 新的使用者資料
6. 前端更新頁面 → 回到查看模式

### 失敗情況
- 姓名為空 → 顯示「姓名必填」
- 姓名超過 50 字 → 顯示「姓名不超過 50 字」
- 簡介超過 500 字 → 顯示「簡介不超過 500 字」
- 頭像檔案 > 5MB → 顯示「檔案大小不超過 5MB」
- 頭像格式錯誤 → 顯示「僅支援 JPG 和 PNG」
- 上傳失敗（500 error）→ 顯示「保存失敗，請稍後重試」
- 非登入使用者 → 重定向到登入頁

### 邊界條件
- 編輯中途離開（不保存）→ 資料不改變
- 編輯時其他地方修改了檔案 → 後端應用最新的
- 同時開 2 個編輯窗口 → 最後一個保存贏
- 連續快速點擊保存 → 只執行一次（防止重複）
- 下載頭像→上傳相同的圖→應該成功（冪等性）

### 驗收條件
- [ ] 使用者可進入編輯模式
- [ ] 表單預填當前資訊
- [ ] 可修改姓名、頭像、簡介
- [ ] 姓名驗證正常
- [ ] 簡介字數驗證正常
- [ ] 頭像上傳驗證正常
- [ ] 保存時發送 PATCH /api/profile
- [ ] 伺服器回應成功時，頁面更新
- [ ] 伺服器回應失敗時，顯示錯誤訊息
- [ ] 取消編輯不保存變更
- [ ] 防止重複提交
```

### Step 2：整理成規格檔

創建 `spec-edit-profile.md`，保存規格。

## Phase 2：澄清問題（10 分鐘）

### Step 1：列出澄清點

給 Agent 規格後，問以下問題：

```
「我有幾個澄清點：

1. 頭像修改流程：
   a) 使用者點『選擇圖片』→ 選檔案 → 預覽 → 確認保存？
   b) 還是直接選檔案 → 自動上傳？

2. 移除頭像：
   - 能刪掉現有頭像嗎？刪掉後用預設頭像？
   - 還是必須保留一個？

3. 編輯完但還沒點保存，使用者關掉頁面：
   - 是否需要『確定要離開嗎？有未保存的變更』提示？

4. 後端 API：
   - PATCH /api/profile 的 request body 格式？
   - response 格式是什麼？

5. 頭像 URL：
   - 上傳後馬上能取得新 URL 嗎？
   - 還是需要輪詢？

等等，請優先澄清前 3 點。」
```

### Step 2：記錄 Agent 的回答

Agent 回答：

```
好的，根據你的規格，我做出以下假設
（如果不對請糾正）：

1. 頭像修改流程：
   選擇圖片 → 預覽 → 點『確認』自動上傳
   （等待上傳完成再允許點保存）

2. 移除頭像：
   可以刪除，會用預設頭像

3. 離開頁面：
   加上『確定要離開嗎？』提示

4. API 設計：
   PATCH /api/profile
   Request:
   {
     displayName?: string,
     bio?: string,
     avatar?: File | null
   }
   
   Response (200):
   {
     id, email, displayName, avatar, bio, updatedAt
   }

5. 頭像 URL：
   上傳後馬上在 response 中獲得新 URL

這些假設對嗎？
```

### Step 3：確認

```
「都對。其他的按你的設計做。」
```

## Phase 3：制定計畫（15 分鐘）

### Step 1：要求 Agent 提出計畫

```
「現在給我詳細的實作計畫。

包括：

```

### Step 2：Agent 提出計畫

```markdown
## 『編輯檔案』功能實作計畫

  • 切換編輯模式的狀態管理
  • 顯示表單（編輯模式）或資訊（查看模式）

- 新增 src/components/EditProfileForm.tsx
  • 表單元件
  • 欄位驗證
  • 實時字數顯示（簡介）

- 新增 src/hooks/useEditProfile.ts
  • 管理編輯狀態
  • 處理頭像上傳邏輯
  • 處理表單提交

### 後端改動
- 修改或新增 PATCH /api/profile 端點
  • 接收 displayName, bio, avatar
  • 驗證輸入
  • 處理頭像上傳/儲存
  • 更新 DB
  • 回傳新的使用者資料

- 頭像儲存策略：
  • 上傳到 /uploads 目錄（或 CDN）
  • 舊頭像刪除
  • 生成新 URL

### 實作順序
1. **後端：** API 端點設計 + 驗證邏輯
   （前端可以基於此設計表單）

2. **後端：** 實作 PATCH /api/profile 端點

3. **後端：** 單元測試

4. **前端：** EditProfileForm 元件

5. **前端：** Profile 頁面集成

6. **前端：** 整合測試

### 依賴關係
```
後端 API 設計
    ↓
後端實作 ← 前端可以並行開發（基於設計）
    ↓
前端表單
    ↓
整合

可以並行！
```

### 測試計畫
- 後端單元測試：
  • 各種驗證規則（姓名、簡介、頭像）
  • 成功修改
  • 失敗情況

- 前端單元測試：
  • 表單驗證（即時反饋）
  • 狀態管理

- 整合測試：
  • 完整流程（進入編輯 → 修改 → 保存 → 查看）

- 手動測試清單：
  • 各個瀏覽器
  • 手機響應式
  • 邊界情況（網路慢、上傳失敗等）
```

## Standard 工作流最佳實踐

### ✅ 做這些事

```
1. 規格要清楚，但不要過度詳細
   ✅ 3-5 頁的規格足夠
   ❌ 20 頁的超詳細設計文件

2. 澄清階段一定要做
   ✅ 5-10 個澄清問題
   ❌ 跳過澄清階段

3. 先有計畫再寫程式碼
   ✅ Agent 先提計畫，你審查
   ❌ 直接寫程式碼

4. 後端和前端可以並行
   ✅ 基於 API 設計，兩邊同時進行
   ❌ 後端做完前端才開始

5. 邊寫邊測
   ✅ 後端做完立馬單測
   ✅ 前端做完立馬驗證
   ❌ 全部寫完再測（發現問題太晚）
```

### ❌ 避免這些事

```
1. 規格太模糊
   ❌ 「使用者可以編輯檔案」
   → 什麼欄位可編？怎麼驗證？邊界怎麼處理？

2. 跳過澄清
   ❌ 規格寫了，直接實作
   → 實作中發現理解錯誤，返工

3. 沒有計畫就開始
   ❌ Agent 直接開始寫程式碼
   → 不知道要做什麼順序，互相依賴

4. 不驗證中間結果
   ❌ 等全部做完再測試
   → 發現問題時代價最高

5. 規格和實作不同步
   ❌ 規格說要 A，實作做了 B
   → 沒有人檢查是否符合規格
```

## Standard 工作流的陷阱

### 陷阱 1：規格寫得太詳細

```
你寫了 20 頁的設計文件，包括：
- 每個按鈕的位置（應該交給設計師）
- 資料庫設計細節（應該交給 Agent）
- 演算法實作（應該交給 Agent）

結果：
- 文件太長，Agent 讀不完
- 過度限制了 Agent 的設計空間
- 如果後來要改，要改文件+程式碼

解決：
規格描述「做什麼」和「驗收標準」
不描述「怎麼做」
```

### 陷阱 2：澄清階段忽視重要問題

```
你問了 5 個小問題，但沒問：
- 「能同時開 2 個編輯窗口嗎？」
- 「如果用戶中途網路斷了怎麼辦？」
- 「編輯和其他人的修改衝突怎麼辦？」

結果：實作中發現，又要改。

解決：澄清階段想清楚「邊界條件」和「錯誤情況」
```

### 陷阱 3：計畫沒有標記依賴

```
計畫說：
1. 寫後端
2. 寫前端
3. 寫測試

看起來順序清楚，但：
- 什麼時候可以開始前端？（等後端 API 定義）
- 什麼時候可以寫測試？（實作中邊寫邊測）

結果：前端等了很久，後端實作了 30% 才發現 API 設計錯了。

解決：計畫中明確標記「並行點」和「同步點」
```

### 陷阱 4：驗證不充分

```
你檢查了：
✅ 功能能用
❌ 但沒檢查邊界情況
❌ 沒在手機上試
❌ 沒測網路慢時的情況

結果：上線後，邊界情況出問題。

解決：BDD scenarios 覆蓋所有情況（快樂路徑 + 錯誤 + 邊界）
```
