## 🎬 Full 工作流概覽

```
特徵：
  ✅ 複雜度高（6+ 分）
  ✅ 涉及多個系統/服務
  ✅ 需要詳細規劃和風險評估
  ✅ 有多個審查點
  ✅ 可能涉及外部 API、金錢、權限

流程：
  Phase 0: 規格 + 澄清
    ↓
  Phase 1: 研究 + 計畫
    ↓
  🛑 人類審查（你要認真看）
    ↓
  Phase 2: 任務分解
    ↓
  Phase 3: 逐步實作
    ↓
  Phase 4: 整合驗證
    ↓
  🛑 驗收測試

時間：2-5 天
文件：spec + 研究筆記 + 計畫 + 任務列表
成功率：99%
```

## 案例：第三方金流整合（綠界 ECPay）

### 背景故事

你的電商平台目前用簡單的轉帳功能。

PM 說：「太原始了，我們要整合綠界 ECPay，支援信用卡、ATM 轉帳、超商代收。」

### 複雜度評估

```
Q1: 訂單系統 + 支付系統 + 綠界 API = 2 分
Q2: 轉帳（不可逆）+ 權限（admin 設置）= 3 分
Q3: 需要 transactions/payments 表 = 2 分
Q4: 呼叫綠界 API = 2 分
──────────────────────────────────────
總分：9 分 → Full 工作流 ✅✅✅
```

## Phase 0：規格與澄清（2 小時）

### Step 1：寫詳細規格

```markdown
## 綠界 ECPay 支付整合規格

### 1. 目標
用戶可以通過綠界 ECPay 支付訂單，
支援信用卡、ATM、超商代收多種支付方式

### 2. 支付流程

#### 正常流程
1. 用戶確認訂單 → 點「去支付」
2. 系統生成支付表單，跳轉綠界支付頁
3. 用戶在綠界選擇支付方式並完成支付
4. 綠界返回結果給我們
5. 我們根據結果更新訂單狀態

#### 支付方式
- 信用卡（即時支付）
- ATM 轉帳（用戶完成轉帳後綠界通知）
- 超商代收（用戶選擇門市，綠界寄收據）

### 3. 資料流

```
我們的系統
    ↓
[生成訂單]
    ↓
[重定向到綠界]
    ↓
綠界支付頁
    ↓
[用戶支付]
    ↓
綠界 → 回調我們的 webhook
    ↓
[更新訂單狀態]
    ↓
[通知用戶]
```

### 4. API 設計

#### 1) POST /api/orders/:orderId/payment
功能：生成支付表單，跳轉綠界

Request:
```
{
  orderId: string,
  returnUrl?: string  // 支付完成後返回位置
}
```

Response:
```
{
  redirect_url: "綠界的支付頁面 URL",
  merchantTradeNo: "我們的訂單號"
}
```

#### 2) POST /api/webhook/ecpay
功能：綠界回調，通知支付結果

Body (from ECPay):
```
{
  merchantTradeNo,    // 我們的訂單號
  paymentType,        // credit_card / atm / ...
  paymentDate,
  tradeStatus,        // 1=成功, 0=失敗
  ...
  checkMacValue       // 簽章驗證
}
```

Response:
```
{
  status: "success" // 必須回應，否則綠界會重試
}
```

#### 3) GET /api/orders/:orderId/payment-status
功能：查詢支付狀態

Response:
```
{
  orderId,
  status,           // pending / completed / failed
  paymentMethod,    // 支付方式
  amount,
  paidAt
}
```

### 5. 邊界條件

#### 支付狀態管理
- 訂單初始狀態：pending
- 用戶點「去支付」→ 狀態變 processing
- 綠界確認支付 → 狀態變 completed
- 支付失敗/超時 → 狀態回到 pending（用戶可重試）

#### 安全考慮
- 簽章驗證：每個來自綠界的請求都要驗籤
- 冪等性：同一筆訂單收到重複回調要能處理
- 金額驗證：確認支付金額與訂單金額相符
- 時間窗口：支付請求超過 30 分鐘未完成自動作廢

#### 異常情況
- 綠界 API 超時 → 重試 3 次
- 網路斷掉 → 用戶稍後重試，不丟失訂單
- 綠界回調丟失 → 用戶可查詢狀態，手動更新（管理員功能）
- 金額不符 → 警告，不更新訂單狀態，記錄異常

### 6. 環境設置
- 測試環境：用綠界測試帳號和沙箱 API
- 生產環境：生產帳號和生產 API
- 金鑰：存在環境變數，不 commit

### 7. 驗收條件
- [ ] 能生成綠界支付表單
- [ ] 支援信用卡支付
- [ ] 支援 ATM 轉帳
- [ ] 支援超商代收
- [ ] 綠界回調正常觸發
- [ ] 訂單狀態正確更新
- [ ] 簽章驗證通過
- [ ] 異常情況能正確處理
- [ ] 沙箱環境測試通過
- [ ] 隱私和安全相符規範
```

```markdown
#### 綠界 API 特點

- 回應簽章：同樣方式驗證

### B. 系統設計

```
前端
  ↓

```
### F. 風險評估

#### 高風險
- ⚠️ 簽章驗證失敗
  → 影響：無法確認綠界回調是真實的
  → 解決：詳細測試，對接時核實簽章公式

- ⚠️ 重複計費（同一訂單支付多次）
  → 影響：財務損失
  → 解決：冪等性檢查，database unique 約束

#### 中風險
- ⚠️ 綠界 API 超時
  → 解決：重試邏輯 + 超時設定

- ⚠️ 回調丟失
  → 解決：支援狀態輪詢查詢

#### 低風險
- ⚠️ 測試環境配置錯誤
  → 解決：詳細文件，驗證清單
```
