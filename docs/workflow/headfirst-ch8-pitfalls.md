## 陷阱 1：跳過規格，直接寫程式碼

### 症狀

```
你說：「給我寫使用者登入功能」
3 小時後，Agent 給你 500 行程式碼

你檢查時發現：
- 密碼驗證規則和預期不符
- 少了「記住我」功能
- 沒考慮帳號鎖定
- 重寫花了 4 小時
```

### 原因

```
「規格太麻煩，直接寫吧」
  ↓
Agent 猜測
  ↓
猜測 ≠ 實際需求
  ↓
返工
```

### 對策

```
✅ 永遠先寫規格，即使只是簡單功能

Lite 工作流：1 句話的規格就夠
  「把按鈕改成綠色」

Standard 工作流：3-5 頁的規格
  目標、場景、驗收條件

Full 工作流：5-10 頁的詳細規格
  包括所有邊界情況

時間投入規格 < 最後返工的時間
```

### 實例

```
❌ 壞：
  「寫個支付功能」
  → Agent 實作了 5 種支付方式（只需要 1 種）
  → 返工

✅ 好：
  「寫支付功能，只支援信用卡，金額 ≥ $10」
  → Agent 直接做對
  → 一次成功
```

## 陷阱 2：規格太詳細

### 症狀

```
你寫了 30 頁的規格，包括：
- 每個按鈕的 RGB 值
- 資料庫的第三正規化設計
- 排序演算法的具體選擇
- 每個變數的命名規則

Agent 的回應：
「規格太長了，我只看完 20%。」
```

### 原因

```
過度規範 = 試圖控制 Agent 的每個決定
  ↓
規格篇幅爆炸
  ↓
沒人讀完
  ↓
反而遺漏重要細節
```

### 對策

```
✅ 規格應該是：

目標：「做什麼」
場景：「在什麼情況下」
驗收條件：「怎麼驗證是對的」

❌ 規格不應該是：

實作細節：「怎麼做」留給 Agent
技術選擇：「用什麼框架」留給 Agent
代碼風格：「如何命名」有 linter 或編碼規範

經驗法則：規格 1-5 頁就足夠
```

### 實例

```
❌ 過度詳細：
  「使用者登入功能

   頁面佈局：
   - 頂部 logo (200x50px)
   - 中央表單 (400px wide)
   - Email 欄位 (input type=email)
   - 密碼欄位 (input type=password)
   - 按鈕背景色 #4CAF50
   - 字體 Roboto 12px
   - border-radius 4px
   
   資料庫：
   - 使用 bcrypt 雜湊密碼
   - salt rounds = 10
   - 用 JWT，payload 包含 {id, email}
   
   ...20 頁以上」
  → Agent 被規格壓倒，容易遺漏重要點

✅ 精簡規格：
  「使用者登入功能
  
   目標：使用者用 email 和密碼登入，回傳 JWT
   
   驗收條件：
   - [ ] 正確的帳密回傳有效 JWT
   - [ ] 錯誤帳密回傳 401
   - [ ] JWT 24 小時內有效
   - [ ] 密碼安全儲存（雜湊）
   
   邊界：
   - 連續失敗 5 次鎖定 15 分鐘
   - 舊 JWT 使用者 logout 後失效」
  → 清楚，簡潔，Agent 能快速理解
```

## 陷阱 3：忘記問澄清問題

### 症狀

```
你：「寫個登入功能」
規格：「用戶用 email 和密碼登入」

2 小時後 Agent 完成：
- 支援第三方登入（你沒要求）
- 實作了找回密碼（你沒要求）
- 支援 SMS 驗證（你沒要求）

你：「我只要基本登入啊」
返工 ❌
```

### 原因

```
「我的規格已經很清楚了」← 你的想像
  ↓
但規格沒寫清楚的地方，Agent 就猜
  ↓
猜測經常不對
```

### 對策

```
✅ 澄清問題要問「邊界和假設」：

「關於登入功能，我有幾個問題：

1. 是否支援第三方登入（Google、Facebook）？
2. 是否支援『記住我』？
3. 連續失敗怎麼辦？鎖定嗎？多久？
4. 舊 token 怎麼處理？
5. 忘記密碼功能現在需要嗎？」

不要問技術問題（那是 Agent 的工作）：
❌ 「怎麼儲存密碼？」
❌ 「用什麼加密演算法？」
❌ 「JWT 還是 session？」
```

### 實例

```
❌ 無澄清：
  Agent 和你的理解完全不同
  返工 2-3 次

✅ 有澄清：
  Agent 按你的期望做
  一次通過
```

## 陷阱 4：計畫不清楚

### 症狀

```
Agent 的計畫：
「步驟 1：寫後端
 步驟 2：寫前端
 步驟 3：測試」

看起來清楚，但：
- 什麼時候前端可以開始？（等後端 API 定義）
- 什麼時候開始寫測試？（邊寫邊測還是最後？）
- 有沒有互相依賴？
- 如果後端改 API 設計，前端怎麼辦？

結果：邊做邊發現問題，進度混亂
```

### 原因

```
計畫太概括 = 不清楚實際依賴關係
```

### 對策

```
✅ 好的計畫應該標記：

Task A (2 天)
  ↓
Task B (1 天) ← 需要 A 完成
  ↓
Task C (1 天) ← 需要 B 完成

並行點：
  Task A 和 Task D 可以同時進行
  Task D (0.5 天)

同步點：
  Task A + D 都完成後，進入 Task B
```

### 實例

```
❌ 不清楚的計畫：
  「1. 後端 API
   2. 前端表單
   3. 測試」
   
✅ 清楚的計畫：
  「Task 1: API 契約定義 (0.5 天)
   ├─ Task 2: 後端實作 (1.5 天)
   ├─ Task 3: 前端實作 (1 天) [等待 Task 1]
   └─ Task 4: 整合測試 (1 天) [等待 Task 2, 3]
   
   並行：Task 2 和 3 可同時進行（基於 Task 1 結果）」
```

## 陷阱 5：複雜度評估錯誤

### 症狀

#### 高估複雜度

```
你以為：「新增表單欄位，Full 工作流」
實際上：只是前端改動，Lite 就夠

結果：花了 3 天做應該 30 分鐘的工作
```

#### 低估複雜度

```
你以為：「修改訂單狀態，Lite 工作流」
實際上：涉及金流、權限、併發

結果：開始做才發現複雜，匆忙返工
```

### 原因

```
沒有系統地評估複雜度
```

### 對策

```
✅ 用四問題法快速評估：

Q1: 涉及多少模組？ (1=0分, 2+=2分)
Q2: 有權限、並發、不可逆操作？ (否=0分, 是=3分)
Q3: DB Schema 變更？ (否=0分, 是=2分)
Q4: 外部 API？ (否=0分, 是=2分)

總分 0-2 → Lite
總分 3-5 → Standard
總分 6+ → Full

按分數選工作流，不是憑感覺
```

### 實例

```
「新增表單欄位『公司名稱』」

快速評估：
Q1: 只改前端表單 = 0 分
Q2: 沒有特殊問題 = 0 分
Q3: 欄位已存在，不改 DB = 0 分
Q4: 不涉及外部 API = 0 分
總分：0 分 → Lite ✓

vs.

「整合金流 API」

Q1: 前端 + 後端 + 第三方 = 2 分
Q2: 不可逆操作 = 3 分
Q3: 新增 transactions 表 = 2 分
Q4: 調用金流 API = 2 分
總分：9 分 → Full ✓
```

## 陷阱 6：沒有驗證中間結果

### 症狀

```
Agent 完成後端，你沒有檢查
Agent 完成前端，你沒有檢查
最後整合時發現：
- API 設計不對
- 前端理解錯誤
- 數據格式不匹配

返工 ❌
```

### 原因

```
「等全部做完再測」
  ↓
發現問題時代價最高
  ↓
修復時間 > 預期時間
```

### 對策

```
✅ 邊做邊驗證

標準工作流：
  ✅ 後端完成 → 驗證 API 正常
  ✅ 前端完成 → 驗證和後端對接
  ✅ 整合完成 → 完整流程測試

Full 工作流：
  ✅ 每個任務完成後驗證
  ✅ 有明確的檢查點
  ✅ 檢查點不通過不進入下個任務
```

### 實例

```
❌ 沒有驗證：
  Day 1-3: 各自做各自的，不檢查
  Day 4: 整合時發現 10 個問題
  Day 5-6: 返工
  → 共花 6 天

✅ 邊做邊驗證：
  Day 1 end: API 驗證 ✓
  Day 2 end: 前端對接驗證 ✓
  Day 3 end: 完整流程驗證 ✓
  → 共花 3 天
```

## 陷阱 7：BDD 覆蓋不足

### 症狀

```
你寫了 BDD 情境，但只涵蓋「快樂路徑」：

Scenario: 成功登入
  ... ✓

但沒有涵蓋：
- 密碼錯誤怎麼辦？
- 帳號不存在怎麼辦？
- 帳號被鎖定怎麼辦？
- 同時 1000 人登入怎麼辦？

結果：這些邊界情況上線後才出現 bug
```

### 原因

```
只想著「正常情況」，忽略了「異常情況」
```

### 對策

```
✅ BDD 要涵蓋三種場景：

1. 快樂路徑（happy path）
   └─ 用戶做正確的事，系統給正確的回應

2. 錯誤路徑（error path）
   └─ 用戶或系統出錯，系統給合理的錯誤提示

3. 邊界路徑（edge case）
   └─ 邊界條件、壓力測試、特殊情況

經驗法則：
  每個功能至少 5-10 個 BDD 情境
  包括：1 個快樂路徑 + 3-5 個錯誤 + 1-2 個邊界
```

### 實例

```
❌ 不足的 BDD：
  「Scenario: 登入成功」
  就一個情境

✅ 充分的 BDD：
  Scenario 1: 正確帳密登入成功
  Scenario 2: 密碼錯誤
  Scenario 3: 帳號不存在
  Scenario 4: 帳號被鎖定
  Scenario 5: 同時多人登入
  Scenario 6: 網路超時
  
  6 個情境覆蓋了大多數情況
```

## 陷阱 8：Agent 的輸出沒有檢查就信任

### 症狀

```
Agent：「我寫好了，所有測試都通過」
你：「好的，commit」

上線後發現：
- 測試其實沒覆蓋關鍵路徑
- 只跑了自己寫的單元測試，沒有整合測試
- SQL injection 漏洞沒被發現

用戶投訴 ❌
```

### 原因

```
「Agent 說的就是對」← 錯誤假設
```

### 對策

```
✅ 信任但驗證

不要盲目信任 Agent，要檢查：

代碼層面：
  □ 代碼審查（邏輯、邊界、安全）
  □ 測試覆蓋率 ≥ 80%
  □ 沒有 security warning

功能層面：
  □ 手動測試所有 BDD 情境
  □ 測試邊界情況
  □ 跨瀏覽器測試
  □ 性能測試

安全層面：
  □ SQL injection 防護
  □ XSS 防護
  □ CSRF 防護
  □ 認證和授權檢查
```

### 實例

```
❌ 盲目信任：
  Agent：「測試通過」
  你：「好的」
  上線後出現 bug ❌

✅ 信任但驗證：
  Agent：「測試通過，覆蓋率 85%」
  你：檢查代碼 → 發現 SQL injection 漏洞
  修復後再上線 ✓
```

## 陷阱 9：改動影響範圍評估錯誤

### 症狀

```
你改了「日期格式函式」的輸出
想著只影響首頁

結果：
- 報表頁面日期也變了（可能不想要）
- API 回應格式改了（破壞了移動 App）
- 資料匯出格式改了（用戶無法識別）

返工 ❌
```

### 原因

```
沒有評估函式被使用的所有地方
```

### 對策

```
✅ 改動前要 check：

1. 搜索：這個函式/欄位在哪裡被使用？
2. 影響：改動會影響哪些頁面/功能？
3. 評估：是否影響超出預期？
4. 決策：
   - 如果只影響預期地點，可以改
   - 如果影響超出預期，升級工作流

給 Agent 的指令：
「改這個函式時，確保只影響首頁。
 搜索其他地方是否使用了這個函式，
 如果有，告訴我會有什麼影響。」
```

### 實例

```
❌ 沒有評估影響：
  改 formatDate 函式
  只考慮了首頁
  結果影響了 5 個其他頁面

✅ 評估影響：
  搜索 formatDate 被使用在：
  - HomePage.tsx ✓
  - ReportPage.tsx ✗ (不想改)
  - ExportService.ts ✗ (不想改)
  
  決策：新增新函式 formatHomeDate，
  或只在 HomePage 修改
```

## 陷阱 10：沒有建立反饋回路

### 症狀

```
你和 Agent 一起做了 10 個功能
結果：
- 很多時候 Agent 理解錯誤
- 同樣的問題重複出現
- 效率沒有提升

但你從未反思過「怎麼改進」
```

### 原因

```
「做完就算」，沒有回顧和改進
```

### 對策

```
✅ 建立反饋回路

每個功能完成後，問自己：

1. 哪裡做得好？
   □ 規格清晰？
   □ Agent 很快理解？
   □ 一次通過？

2. 哪裡做得不好？
   □ 返工多少次？
   □ 什麼地方 Agent 理解錯誤？
   □ 什麼地方浪費了時間？

3. 下次怎麼改進？
   □ 改進規格寫法？
   □ 問更多澄清問題？
   □ 提供更多上下文？
   □ 使用更清晰的例子？

每週回顧一次，改進工作流
```

### 實例

```
❌ 沒有反饋回路：
  功能 1: 返工 2 次
  功能 2: 返工 2 次
  功能 3: 返工 2 次
  ...
  一直在重複同樣的錯誤

✅ 建立反饋回路：
  功能 1: 返工 2 次 → 發現「規格不清」
  功能 2: 改進規格方法 → 返工 1 次
  功能 3: 繼續改進 → 返工 0 次
  功能 4: 返工 0 次
  ...
  效率逐漸提升
```

## 額外陷阱：Agent 變成瓶頸

### 症狀

```
你依賴 Agent 太多：
- 什麼都要 Agent 來決定
- 自己不思考，等 Agent 的答案
- Agent 一犯錯，你就卡住了

結果：
- 浪費 Agent 的 token
- 開發進度不可控
- 依然沒學到東西
```

### 原因

```
把 Agent 當成「自動機器」，而不是「協作夥伴」
```

### 對策

```
✅ 你應該是決策者，Agent 是執行者

你的職責：
  □ 理解需求（和 PM 溝通）
  □ 評估複雜度（決定工作流）
  □ 寫規格（描述「要做什麼」）
  □ 澄清問題（確認理解）
  □ 審查計畫（確認方向）
  □ 驗證結果（檢查品質）
  □ 做決策（遇到問題時）

Agent 的職責：
  □ 寫程式碼
  □ 提出實作方案
  □ 執行計畫
  □ 執行測試
  □ 提供技術建議

分工清楚，才能高效協作
```

## 🧠 快速診斷：你掉坑了嗎？

```
如果你的回答超過 3 個「是」，
說明你可能掉坑了：

□ 規格不清楚，Agent 經常理解錯誤
□ 返工很頻繁（超過 30%）
□ 測試發現大量 bug
□ Agent 花時間做了無用功
□ 進度不可控
□ 相同問題重複出現
□ 手機和桌面版本總有一個出問題
□ 安全問題總是事後才發現
□ 沒有明確的驗收標準
□ 用戶反饋：「這不是我要的」
```

如果超過 3 個，停下來反思，改進流程。
