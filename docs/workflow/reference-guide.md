## 1️⃣ 四句咒語速記

### 完整版

```
📋 /specify
   「先說清楚要做什麼」
   ↓ 寫規格

🔍 /clarify
   「把模糊的地方問清楚」
   ↓ 澄清問題

🗺️  /plan
   「畫一張施工藍圖」
   ↓ 制定計畫

🔨 /implement
   「按圖施工，步步驗證」
   ↓ 實作和驗證
```

### 簡潔版

```
Specify → Clarify → Plan → Implement
說清  →   問明   → 畫圖  →   按圖做
```

### 對應工作流

```
Lite:     Specify → Implement (跳過 Clarify 和 Plan)
Standard: Specify → Clarify → Plan → Implement
Full:     Specify → Clarify → Research → Plan → Implement
```

## 2️⃣ 四問題複雜度評估

### 評估表

```
┌─────────────────────────────────────────┐
│  四問題複雜度評估法                      │
├─────────────────────────────────────────┤

Q1: 涉及多少模組或服務？
    □ 1 個單一模組           → 0 分
    □ 2 個或以上模組         → 2 分

Q2: 有權限、並發或不可逆操作嗎？
    □ 都沒有                 → 0 分
    □ 至少有一個             → 3 分

Q3: 涉及 DB Schema 變更嗎？
    □ 不涉及（只讀、只改應用邏輯）→ 0 分
    □ 涉及（新表、新欄位、索引）  → 2 分

Q4: 涉及外部 API 整合嗎？
    □ 不涉及                 → 0 分
    □ 涉及第三方 API         → 2 分

─────────────────────────────────────────
總分：_____ 分

0-2 分  →  Lite 工作流    (< 30 分鐘)
3-5 分  →  Standard 工作流 (1-2 小時)
6+ 分   →  Full 工作流    (2-5 天)
└─────────────────────────────────────────┘
```

### 快速判斷表

```
功能               │ Q1 │ Q2 │ Q3 │ Q4 │ 分 │ 工作流
─────────────────│────│────│────│────│────│──────────
修改按鈕顏色      │ 0  │ 0  │ 0  │ 0  │ 0  │ Lite
修正日期格式      │ 0  │ 0  │ 0  │ 0  │ 0  │ Lite
新增表單欄位      │ 0  │ 0  │ 0  │ 0  │ 0  │ Lite
修改文案          │ 0  │ 0  │ 0  │ 0  │ 0  │ Lite
修復簡單 Bug      │ 0  │ 0  │ 0  │ 0  │ 0  │ Lite
─────────────────│────│────│────│────│────│──────────
新增 API 端點     │ 2  │ 0  │ 0  │ 0  │ 2  │ Lite/Std
編輯個人檔案      │ 2  │ 0  │ 0  │ 0  │ 2  │ Lite/Std
評論系統          │ 2  │ 3  │ 2  │ 0  │ 7  │ Full
─────────────────│────│────│────│────│────│──────────
使用者邀請        │ 2  │ 3  │ 2  │ 0  │ 7  │ Full
金流整合          │ 2  │ 3  │ 2  │ 2  │ 9  │ Full
OAuth 整合        │ 2  │ 0  │ 0  │ 2  │ 4  │ Standard
Email 通知        │ 2  │ 0  │ 0  │ 2  │ 4  │ Standard
```

## 3️⃣ 規格範本

### Lite 規格範本

```markdown
## [功能名稱]

### 目標
用 1 句話說明目的

### 改動
當前：...
應該：...

### 驗證
[怎麼檢查是對的]
```

### Standard 規格範本

```markdown
## [功能名稱]規格

### 1. 目標
用 1-2 句話說明這個功能的目的

### 2. 使用者場景
1. 使用者做什麼...
2. 系統回應什麼...
3. ...

### 3. 成功流程
輸入：...
處理：...
輸出：...

### 4. 失敗情況
- 情況 1 → 錯誤訊息 X
- 情況 2 → 錯誤訊息 Y

### 5. 邊界條件
- 邊界 1：...
- 邊界 2：...

### 6. 驗收條件
- [ ] 功能 1 可用
- [ ] 功能 2 可用
- [ ] 驗證規則 X 有效
- [ ] 錯誤訊息正確
- [ ] 邊界情況正常處理
```

### Full 規格範本

```markdown
## [功能名稱]規格

### 1. 目標

### 2. 上下文
背景、為什麼需要、涉及的其他系統

### 3. 使用者場景
詳細步驟...

### 4. 成功流程

### 5. 失敗流程（多個）

### 6. 邊界條件（5+ 個）

### 7. 安全考慮
- 認證和授權
- 資料隱私
- 攻擊防護

### 8. 性能要求
- 回應時間
- 併發支持
- 資料量上限

### 9. 相依性
- 需要其他系統什麼支持

### 10. 驗收條件（10+ 個）
```

## 4️⃣ BDD 情境範本

### 最小範本

```gherkin
Feature: [功能名稱]

  Scenario: [場景名稱]
    Given [前置條件]
    When [使用者動作]
    Then [預期結果]
```

### 標準範本

```gherkin
Feature: [功能名稱]
  [簡短描述]

  Background:
    Given [每個 scenario 前都要做的設置]

  Scenario: [快樂路徑]
    Given [前置條件]
    When [使用者動作]
    Then [預期結果]
    And [進一步驗證]

  Scenario: [錯誤情況 1]
    Given [前置條件]
    When [錯誤操作]
    Then [錯誤訊息]

  Scenario: [邊界情況]
    Given [邊界條件]
    When [操作]
    Then [特殊處理]
```

### 實例

```gherkin
Feature: 使用者登入

  Scenario: 成功登入
    Given 使用者在登入頁面
    When 輸入正確的 email 和密碼
    Then 顯示首頁
    And JWT token 有效

  Scenario: 密碼錯誤
    Given 使用者在登入頁面
    When 輸入錯誤的密碼
    Then 顯示「帳號或密碼錯誤」
    And 不發送任何 token

  Scenario: 連續失敗 5 次
    Given 使用者已失敗登入 5 次
    When 再次嘗試登入
    Then 顯示「帳號已鎖定」
    And 顯示「15 分鐘後重試」
```

## 5️⃣ 工作流選擇決策樹

### 流程圖

```
開始
  ↓
複雜度評估（四問題法）
  ↓
─────┬─────────┬──────────
0-2 分│ 3-5 分  │ 6+ 分
     ↓         ↓          ↓
   Lite    Standard     Full
   ↓         ↓          ↓
 [A]       [B]        [C]
```

### A. Lite 工作流決策

```
需求明確嗎？
  ├─ YES → 直接做
  └─ NO  → 寫 1-2 句規格

涉及多個地方嗎？
  ├─ YES → 升級為 Standard
  └─ NO  → 繼續 Lite

預期時間 < 30 分鐘嗎？
  ├─ YES → 執行 Lite
  └─ NO  → 升級為 Standard
```

### B. Standard 工作流決策

```
有規格嗎？
  ├─ YES → 進入澄清
  └─ NO  → 寫規格（3-5 頁）

澄清完成嗎？
  ├─ YES → 進入計畫
  └─ NO  → 問澄清問題

計畫清楚嗎？
  ├─ YES → 執行實作
  └─ NO  → 重新計畫

有新的複雜性出現嗎？
  ├─ YES → 升級為 Full
  └─ NO  → 繼續 Standard
```

### C. Full 工作流決策

```
規格詳細嗎？
  ├─ YES → 進入澄清
  └─ NO  → 寫詳細規格（5-10 頁）

澄清完成嗎？
  ├─ YES → 進入研究和計畫
  └─ NO  → 問澄清問題（10+ 個）

計畫通過人類審查嗎？
  ├─ YES → 進入任務分解
  └─ NO  → 修改計畫

有檢查點通過嗎？
  ├─ YES → 進入下一個任務
  └─ NO  → 返工或升級時間線

所有檢查點都通過嗎？
  ├─ YES → 進入整合驗證
  └─ NO  → 修復問題

驗收通過嗎？
  ├─ YES → 可上線
  └─ NO  → 返工
```

## 6️⃣ 給 Agent 的指令範本

### Lite 指令

```
「[改什麼] 改成 [新樣子]。
 改完後 [怎麼驗證]。」

例子：
「把首頁按鈕從藍色改成綠色，
 確認在手機和桌面上都正常。」
```

### Standard 指令序列

#### Phase 1：規格

```
「我要做『[功能名稱]』功能。

規格：
[完整規格，目標、場景、驗收條件]

請告訴我：
1. 是否理解了？
2. 有沒有疑問？
3. 有沒有看出我遺漏的？」
```

#### Phase 2：澄清

```
「澄清幾點：

1. [澄清點 1]？
2. [澄清點 2]？
3. [澄清點 3]？

其他的按你的最佳實踐做。」
```

#### Phase 3：計畫

```
「給我實作計畫：

1. 前端改動
2. 後端改動
3. 實作順序（有沒有依賴？）
4. 測試計畫

暫時不用寫程式碼，就給計畫。」
```

#### Phase 4：實作

```
「按計畫開始實作。

優先順序：
1. [優先做]
2. [次優先]

每個部分完成告訴我進度。」
```

### Full 指令序列

#### Phase 0：規格

```
「我們要做『[功能名稱]』。

詳細規格：
[5-10 頁的規格，包括所有邊界]

請列出所有疑問。」
```

#### Phase 1：研究和計畫

```
「[收到澄清後]

請做：
1. 研究相關技術、API、第三方文件
2. 制定詳細實作計畫
3. 識別主要風險
4. 估計時間

給完整的計畫文件，我會審查。」
```

#### Phase 2：任務分解

```
「[計畫通過後]

將計畫分解成具體任務：
1. 每個任務應該 < 1 天
2. 標記依賴關係
3. 標記檢查點
4. 估計時間

給任務列表。」
```

#### Phase 3：實作

```
「按任務清單實作。

每個任務完成後報告：
1. 做了什麼
2. 關鍵代碼改動
3. 怎麼驗證
4. 遇到什麼問題

檢查點不通過不進入下一個任務。」
```

## 7️⃣ 驗收檢查清單

### Lite 驗收清單

```
□ 改動符合預期
□ 沒有破壞其他功能
□ 程式碼風格一致
□ 準備好 commit
```

### Standard 驗收清單

```
規格階段：
□ 規格清楚嗎？
□ 涵蓋邊界情況嗎？
□ Agent 理解了嗎？

澄清階段：
□ 問了 5+ 個澄清問題？
□ Agent 完全理解了嗎？

計畫階段：
□ 計畫清楚嗎？
□ 標記了依賴嗎？
□ 你審查過嗎？

實作階段：
□ 邊寫邊測？
□ 單元測試通過率 > 90%？
□ 沒有 critical bug？

驗證階段：
□ 所有 BDD scenarios 通過？
□ 跨瀏覽器測試？
□ 手機版也正常？
□ 邊界情況驗證？

最終：
□ 代碼審查通過
□ 準備好 commit
```

### Full 驗收清單

```
代碼層面：
□ 代碼審查通過
□ 所有測試通過（單元 + 整合 + E2E）
□ 代碼覆蓋率 > 85%
□ 沒有 security warning
□ 性能符合預期

部署層面：
□ 環境變數正確配置
□ 資料庫遷移已執行
□ 金鑰已安全存儲
□ 監控和告警已設置

文件層面：
□ API 文件已更新
□ 故障排除指南已編寫
□ 部署步驟已記錄

用戶溝通層面：
□ PM 知道上線時間
□ 客服知道新功能
□ 用戶通知已計劃

測試層面：
□ 單元測試覆蓋率 ≥ 85%
□ 整合測試通過
□ E2E 測試通過
□ 邊界情況都測試了
□ 性能測試通過

安全層面：
□ 認證檢查通過
□ 授權檢查通過
□ SQL injection 防護
□ XSS 防護

上線方案：
□ 灰度上線（分階段推出）
□ 監控 critical metrics
□ 有回滾方案
□ 值班人員待命

最終：
□ 準備好上線
```

## 8️⃣ 常見問題快速解答

### Q1：我應該對所有功能都用 Full 工作流嗎？

```
❌ 不應該

取決於複雜度：
- 簡單改動（0-2 分）→ Lite（5-30 分鐘）
- 中等功能（3-5 分）→ Standard（1-2 小時）
- 複雜功能（6+ 分）→ Full（2-5 天）

根據複雜度選工作流，不要過度規劃。
```

### Q2：規格應該寫多詳細？

```
✅ 恰到好處

- 目標清楚
- 場景完整
- 驗收條件具體
- 邊界情況涵蓋

通常 1-5 頁就足夠。
超過 10 頁可能太詳細了。
```

### Q3：澄清問題應該問多少個？

```
Lite：0 個（規格已清楚）
Standard：5-10 個（消除所有模糊點）
Full：10+ 個（確認所有細節）

質量比數量重要。
好的澄清問題 > 隨便問很多
```

### Q4：什麼時候應該升級工作流？

```
發現任何以下情況，立即升級：

Lite → Standard：
  □ 涉及後端改動
  □ 涉及 DB 改動
  □ 影響多個相關功能

Standard → Full：
  □ 新的複雜性出現
  □ 涉及金錢或敏感資料
  □ Agent 說「我需要更多資訊」
  □ 風險高於預期

不要硬撐，評估錯誤比升級工作流的成本更高。
```

### Q5：我怎麼知道 BDD 夠不夠？

```
✅ BDD 應該涵蓋：

1 個快樂路徑：基本功能正常
  [是否能完成正常操作？]

3-5 個錯誤路徑：各種失敗情況
  [是否能正確處理錯誤？]

1-2 個邊界路徑：邊界和壓力
  [是否能在邊界情況下正常？]

經驗法則：每個功能 5-10 個 BDD scenarios
```

### Q6：什麼時候應該驗證中間結果？

```
✅ 應該驗證：

Lite：完成後驗證（一次）
Standard：每個主要部分完成後驗證
Full：每個任務完成後驗證

不要等全部做完再測。
發現問題越早，修復成本越低。
```

### Q7：如何處理需求變更？

```
小變更（5% 範圍內）：
  直接修改，繼續做

中等變更（20% 範圍內）：
  重新評估複雜度，可能升級工作流

大變更（> 20%）：
  停下來，重新規劃
  可能要重新開始
```
