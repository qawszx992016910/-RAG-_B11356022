# ADR-003: 八字排盤採獨立確定性模組

- Status: Accepted
- Date: 2026-04-14
- Deciders: System Architect, Backend Engineer
- Tags: deterministic, calendar, solar-terms, true-solar-time, bazi-engine

## Context

八字系統的所有後續檢索與推理，都建立在正確排盤之上。
若出生年、月、日、時的換算錯誤，後面的格局判定、知識檢索與語言生成都將失真。

節氣、時區、真太陽時、曆法切換，都屬於強確定性計算問題。
這類問題若交由 LLM 根據文字理解自行推算，將有極高機率產生錯誤。

在八字解盤場景中，錯一個柱位，不是小誤差，而是整個查詢基礎錯位。

## Decision

系統將八字排盤設計為獨立的 **Deterministic Module**，不由 LLM 執行。

該模組負責：

- 公曆 / 農曆 / 節氣換算
- 真太陽時計算
- 四柱推算
- 藏干展開
- 十神映射
- 月令與季節判定
- 後續大運流年排算（若有）

LLM 僅使用此模組輸出的結構化結果，不能自行改寫或補算。

## Alternatives Considered

### Option A: 讓 LLM 直接排盤
優點：
- 初期整合快
- 不必先做演算法模組

缺點：
- 容易錯
- 不可驗證
- 無法作為工程系統依賴基礎

### Option B: 外掛第三方排盤 API
優點：
- 開發速度快
- 可快速驗證產品概念

缺點：
- 受制於外部 API
- 透明度不足
- 長期可維運性較差
- 流派與計算細節可能不可控

### Option C: 自建確定性模組
優點：
- 結果可驗證
- 可控性最高
- 長期可維運

缺點：
- 初期工程成本較高
- 需驗證曆法與節氣演算法

## Consequences

### Positive
- 排盤結果可測試、可比對、可回歸
- 系統整體穩定性大幅提高
- 可與後續規則引擎、檢索層穩定整合

### Negative
- 需投入額外開發時間
- 需建立測試樣本與曆法驗證機制

## Implementation Notes

輸出必須採結構化 JSON，至少包含：

- 四柱
- 藏干
- 日主
- 月令
- 十神
- 季節
- 真太陽時是否啟用
- 計算基準資訊

## Decision Drivers

- 排盤錯誤會污染整條推理鏈
- 這是確定性問題，不適合交給機率模型
- 系統需要可驗證與可回歸測試的基礎模組
